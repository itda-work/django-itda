## 0. 한 문장

> 4단계 rowcount 계약은 **UPDATE 경합**을 버틴다. 환불은 **INSERT** 라 조건을 걸 행이 없다.
> 그래서 이번 법은 코드가 아니라 **DB 제약**으로 내려간다 — 3단계에서 본 "전부 지켜지는 층"에 학생이 처음으로 도메인 법을 놓는다.

관통 문장(제안은 AI, 판정은 세계, 확정은 사람)에 한 겹 더: **같은 사건은 두 번 일어나지 않는다.** 재시도는 새 사건이 아니고(멱등키), 경합의 패자는 거짓말 없이 "이미 있다"를 듣는다.

## 1. 켜는 법 — 하나

| ID | 원문(점주) | 시행 형식 | 코드 위치 |
|---|---|---|---|
| `REFUND-003@v1` | **같은 환불을 두 번 처리하지 마라. 한 주문에 환불은 한 번이다.** | **DB 제약**(부분 유일) + 전이 계약(확정은 제안 상태에서만) + 멱등키 | `orders/models.py:Refund.Meta.constraints` · `Refund.approve/reject` · `Refund.apply` |

원문은 시작 상태에서 `agent/prompts/ai_staff.md` "반드시 지켜야 할 것" **4번**으로 먼저 들어간다(점주가 말한 문장 — 4단계와 같은 이사 구조). 완료 상태에서 `→ 코드로 이사됨 (REFUND-003@v1, DB 제약)` 표시를 단다. 문장은 지우지 않는다.

한 법에 시행 면이 셋인 이유는 경합의 모양이 셋이기 때문이다.

| 경합의 모양 | 막는 것 | Django 가 준 자리 |
|---|---|---|
| 다른 두 요청이 같은 주문에 환불을 만든다 (INSERT 경합) | 살아 있는 환불(제안·승인)은 주문당 하나 | `UniqueConstraint(fields=['order'], condition=Q(status__in=[proposed, approved]), name='refund_one_live_per_order')` → `IntegrityError` |
| 같은 요청이 두 번 온다 (재전송) | 같은 열쇠는 같은 답 — 새 환불이 아니라 **그때의 답**을 다시 준다 | `UniqueConstraint(fields=['order', 'idempotency_key'], condition=~Q(idempotency_key=''), name='refund_idempotency_key_per_order')` + 저장된 판정 |
| 점주 둘이 동시에 확정한다 / 승인 뒤 거부 (UPDATE 경합) | 확정은 **제안 상태에서만** | 4단계 모양 그대로: `filter(pk, status=PROPOSED).update(...)` rowcount |

`select_for_update` 는 **비교 대상으로만** 등장한다 — SQLite 는 `has_select_for_update = False` 라 **아무 말 없이 무시**한다. "잠갔다고 믿는데 안 잠긴 잠금"이 이 단계의 실측 하나다(테스트 §4-9).

## 2. 실측 — SQLite 에서 경합 테스트가 성립하는 조건 (핸드오프 §3-2 반영)

핸드오프의 경고: Django 기본 SQLite 테스트 DB 는 **인메모리 shared-cache** 라 두 스레드가 같은 테이블을 만지면 `database table is locked` 가 계약 판정보다 먼저 난다.

프로브(`scratchpad/probe/race.py`, 파일 SQLite · 스레드 2 · `Barrier`) 결과 — 각 3회 반복, 전부 동일:

| 시나리오 | 코드 상태 | DEFERRED | IMMEDIATE |
|---|---|---|---|
| `propose_refund` ×2 동시 (SEED-0003, 3만원 ALLOW) | 4단계 done | `COMMITTED, COMMITTED` — **승인 환불 2건** | 같음 |
| `pay_order` ×2 동시 (SEED-0004) | 4단계 done | `ALLOW, DENY` — 계약이 버틴다 | 같음 |
| `propose_refund` ×2 + 부분 유일 인덱스 | 제약만 심음 | `COMMITTED, IntegrityError` — 1건 | 같음 |

잠금 오류 0건. 따라서 **설계는 `live_server` 가 아니라 "파일 테스트 DB + 스레드 + Barrier"** 로 간다. 이유: `live_server` 는 인메모리 SQLite 에서 연결을 공유하도록 덮어쓰고, 동기화 지점을 심을 수 없어 sol 이 4단계에서 지적한 "시작 동기화 없이 순차 실행도 통과" 문제가 남는다.

성립 조건 네 가지 — 전부 사양에 들어간다.

1. **테스트 DB 를 파일로**: `DATABASES['default']['TEST'] = {'NAME': BASE_DIR / '.test_db.sqlite3'}`. `.gitignore` 에 `.test_db.sqlite3*`. **시작 상태에 넣는다(준비 비용)** — 없으면 시작 상태의 실패가 도메인 실패가 아니라 잠금 실패로 나와 "무엇이 없는가"가 안 보인다.
2. **`@pytest.mark.django_db(transaction=True)`**: 기본 마커는 테스트를 트랜잭션으로 감싸 다른 스레드의 연결이 데이터를 못 본다. `world` fixture 는 이 마커를 따라간다(pytest-django 가 `transactional_db` 로 바꿔 준다).
3. **Barrier 는 잠금 밖에**: 두 스레드를 만나게 하는 지점은 어떤 트랜잭션도 열려 있지 않은 곳이어야 한다. 트랜잭션 안에서 기다리면 `BEGIN IMMEDIATE` 가 서로를 기다려 timeout 까지 멈춘다. 지점은 세 곳으로 고정 — 앱 코드에 훅을 넣지 않고 **`mock.patch` 로 감싼다**(시작·완료 상태 양쪽에 존재하는 메서드).
   - 환불 제안 경합: `Refund.decide`(classmethod — `apply()` 가 `atomic()` 에 들어가기 전에 부른다)
   - 결제 경합: `Order.mark_paid`(호출 직전)
   - 확정 경합: `Refund.approve`(호출 직전)
4. **스레드 끝에서 `connection.close()`**: 안 닫으면 파일 핸들이 남아 teardown 이 흔들린다. 예외는 삼키지 않고 `results` 에 종류를 남긴다 — "예상 밖 예외는 실패"(sol 4단계 지적 반영). `OperationalError` 를 `denied` 로 세지 않는다.

`transaction_mode='IMMEDIATE'` · `timeout=5` · WAL 은 이 두 경로에서는 **결과를 바꾸지 않았다.** 그래도 완료 상태에 넣는 이유는 §3-7 — "읽고 나서 쓰는" 트랜잭션에서 DEFERRED 는 busy 를 기다려 주지 않고 `database is locked` 를 즉시 돌려주기 때문이다. **소거 증명이 아니라 빈도를 줄이는 설정**이고, 지시서에도 그렇게 쓴다.

> **정정(2026-09-06, sol 리뷰 8번)** — 초안은 근거로 "admin 액션이 `changelist_view` 의 `atomic` 에 감싸인다"를 들었다. **틀렸다.** Django 5.2 `options.py` 에서 `response_action` 호출은 `list_editable` 저장용 `transaction.atomic` 블록 **밖**이다. 설정을 넣는 이유는 위 일반론까지이고, admin 을 근거로 들지 않는다.

## 3. 완료 상태(`stage-05-done`) — 구현 diff (학생 코드, 목표 ≈200줄)

### 3-1. `orders/rules.py`

```python
REFUND_003 = 'REFUND-003@v1'
RULE_TEXTS[REFUND_003] = '같은 환불을 두 번 처리하지 마라. 한 주문에 환불은 한 번이다.'
```

### 3-2. `orders/models.py` — `Refund`

- 필드 추가
  - `idempotency_key = CharField('멱등키', max_length=64, blank=True, default='')` — 클라이언트가 준 재전송 식별자. 비어 있으면 "열쇠 없는 요청"이고 제약 대상이 아니다.
  - `verdict = JSONField('판정', default=dict, blank=True)` — 생성 시점의 `Verdict.as_dict()`. 재전송에 **그때의 답**을 돌려주기 위한 저장이다("완전한 멱등 응답 저장" — sol 4단계 #4 예약분).
- `Meta.constraints` 두 개 (§1 표의 이름 그대로).
- `apply(cls, order, amount, reason, requested_by, idempotency_key='')`
  - DENY → 아무것도 쓰지 않음(그대로). **DENY 는 저장하지 않는다** — 재전송은 재판정이고, 같은 입력이면 같은 답이다(7일 경계를 넘긴 재전송만 답이 바뀌며 그때는 새 판정이 정직하다). 지시서에 적는다.
  - 그 외 → `try: with transaction.atomic(): create(...; idempotency_key, verdict=verdict.as_dict()); ALLOW 면 approve(by=None, via=RULE)` / `except IntegrityError:` — **`atomic()` 블록 바깥에서** 잡는다(안에서 잡으면 트랜잭션이 깨진 채 계속된다 — Django 문서 "Controlling transactions explicitly" 경고). 잡은 뒤:
    - `idempotency_key` 가 있고 `(order, idempotency_key)` 행이 있으면 → `replayed_outcome()` — 저장된 판정을 `Verdict(**refund.verdict)` 로 복원, `Outcome(state=REPLAYED, refund=refund)`.
    - 아니면 살아 있는 환불 → `current_outcome()`(ALREADY). 4단계의 "조회 후 생성"이 **"생성 후, 실패하면 조회"** 로 뒤집힌다 — check-then-act 를 act-then-check 로. 이 한 줄이 지시서의 핵심 문장이다.
- `approve(self, by, via=None)` — 전이 계약으로 바꾼다.
  ```python
  with transaction.atomic():
      moved = Refund.objects.filter(pk=self.pk, status=self.Status.PROPOSED).update(
          status=APPROVED, decided_by=by, decided_via=..., decided_at=now)
      if not moved:
          raise InvalidTransition(Verdict(kind=DENY, rule_ids=[REFUND_003],
              reason=f'{REFUND_003}: 제안 상태가 아니다(조건 불일치). {RULE_TEXTS[REFUND_003]}',
              alternatives=['이 환불의 현재 상태를 조회한다']))
      # 메모리 객체 동기화 후 주문 취소(기존과 같음)
  ```
  `reject()` 도 같은 모양. `self.status` 를 사유에 찍지 않는다(4단계 규율). `apply()` 의 ALLOW 경로는 방금 만든 PROPOSED 행이라 그대로 통과한다.

> **정정(2026-09-06, sol 리뷰 2번)** — 위 `apply()` 설계는 **순서가 틀렸다.** `decide()` 를 먼저 부르고 DENY 면 즉시 반환하므로, 승인까지 끝난 건에 같은 열쇠로 재전송했을 때 그 사이 7일이 지났으면 409 DENY 가 나간다. 이미 처리된 사건을 신규 기한 초과 요청처럼 설명하는 것이다.
>
> 확정 순서: **조회(`_existing_outcome`: 같은 열쇠 → REPLAYED / 살아 있는 건 → ALREADY) → `decide()` → 생성(`IntegrityError` → `_resolve_collision`)**. 조회가 앞으로 온 것은 check-then-act 로의 회귀가 **아니다** — 경합에서 두 요청은 조회를 나란히 통과하고, 막는 것은 여전히 제약이다. 조회의 역할이 "막기"에서 "이미 답이 있는 질문에 정직하게 답하기"로 바뀐 것뿐이다. 지시서의 한 문장도 그에 맞춰 "물어본 답으로 막지 마라. 막는 것은 제약이다"로 고친다.
>
> DENY 미저장 설명도 한정한다: "같은 입력이면 같은 답이고 7일 경계에서만 달라진다"는 **부정확하다**(경과 시간이 사유 문장에 들어가므로 글자 단위로는 대개 달라진다). "최초 DENY 는 저장하지 않으며 재요청 시 현재 조건으로 새 판정한다. 동일 본문은 보장하지 않는다"가 맞다.
>
> 같은 열쇠·다른 금액은 **최초 내용 우선**이고 충돌을 검사하지 않는다(고른 정책). 재생 범위는 "저장된 판정과 그 판정의 HTTP 코드"까지이고 객체 상태는 현재 값이다. `ALREADY` 응답은 저장하지 않는다.

### 3-3. `orders/verdict.py`

`Outcome.REPLAYED = 'REPLAYED'` — docstring 에 ALREADY 와의 차이를 적는다: **ALREADY 는 "다른 요청인데 이미 처리된 건이 있다 → 지금 상태"**, **REPLAYED 는 "같은 요청이 다시 왔다 → 그때의 답"**. `Verdict.from_dict()` 클래스메서드 추가(저장 판정 복원).

### 3-4. `orders/services.py`

- `propose_refund(actor, order, amount, reason, idempotency_key='')` — 사전 `filter(...).first()` 를 **서비스 층에서 걷어내고** `Refund.apply` 에 그대로 위임한다. docstring 을 "세계가 막는다"로 바꾼다. (정정: 조회 자체가 사라지는 것이 아니라 모델의 `_existing_outcome` 으로 옮겨 가 **판정 앞에 선다** — 위 §3-2 정정 참조.)
- 확정 쪽은 서비스 함수를 새로 만들지 않는다. `Refund.approve/reject` 를 부르는 세 곳이 `InvalidTransition` 을 받는다:
  - `orders/views.py:approve_refund/reject_refund` → `messages.warning(verdict.reason)` + redirect (409 화면은 콘솔 DENY 용이라 여기선 메시지로 충분).
  - `orders/admin.py:approve_selected/reject_selected` → 건수 분리: `n건 승인, m건은 제안 상태가 아니어서 건너뜀`.
  - `orders/api.py:refund_approve` → **`status != PROPOSED` 사전 검사를 지우고** `try/except InvalidTransition` → `verdict_response(denied.verdict, outcome=ALREADY, refund=...)` 409. 사전 검사가 바로 4단계에 남아 있던 check-then-act 다.

### 3-5. `orders/api.py` — 멱등키 입구

- `refund_create`: `request.headers.get('Idempotency-Key')` 우선, 없으면 body `idempotency_key`. 64자 초과면 400. 서비스에 전달.
- 응답: `outcome == REPLAYED` 면 상태 코드는 **저장된 판정**의 것(ESCALATE 면 202). `refund_json` 에 `idempotency_key` 추가.

### 3-6. `agent/live/mcp_server.py`

`propose_refund(order_id, amount=None, reason='고객 요청', request_id: str | None = None)` — `request_id` 를 `Idempotency-Key` 헤더로. docstring: "같은 요청을 다시 보낼 때는 같은 `request_id` 를 써라 — 새 환불이 아니라 그때의 답을 다시 받는다. `decision` 이 같고 `outcome` 이 `REPLAYED` 다." `_call` 에 `headers` 인자 추가. 이 파일은 임시 구현이므로 이 이상 손대지 않는다.

### 3-7. 잠금 실패는 판정이 아니다 — `config/middleware.py` + settings

- `WorldBusyMiddleware.process_exception`: 잠금 실패면 **503** + `Retry-After: 1`. JSON `{'error': 'busy', 'reason': '세계가 잠겨 있어 판정하지 못했다 — 거부(409)가 아니다. 잠시 후 같은 요청을 다시 보내라.', 'retry_after': 1}`. `Accept` 에 `text/html` 이 있으면 같은 문장을 `HttpResponse(status=503)` 로. 그 외 예외는 건드리지 않는다(500 은 500이다).
- `DATABASES['default']['OPTIONS'] = {'transaction_mode': 'IMMEDIATE', 'timeout': 5, 'init_command': 'PRAGMA journal_mode=WAL;'}` — 주석에 §2 마지막 문단의 한정("빈도를 줄이는 설정, 소거 증명 아님")을 그대로.
- `MIDDLEWARE` 에 등록(맨 앞 근처). "가장 바깥에서 예외를 본다"고 쓰지 않는다 — `process_exception` 은 뷰에서 올라온 예외를 볼 뿐 모든 미들웨어 단계를 덮는 최외곽 catch 가 아니다.

> **정정(2026-09-06, sol 리뷰 7번)** — 판별을 `locked`·`busy` **부분 문자열**로 두면 `no such table: busy_orders` 같은 스키마 오류도 503 이 된다(실측). 확정: 원인 예외(`__cause__`)의 `sqlite_errorcode & 0xFF` 가 `SQLITE_BUSY`·`SQLITE_LOCKED` 인지를 1차로 보고, 코드가 없을 때만 `database is locked`·`database table is locked` 와 **전체 일치**를 본다. `BUSY_REASON` 도 "**이 요청은** 판정하지 못했다"로 한정한다 — admin 다건 액션에서는 앞 건이 이미 커밋됐을 수 있다.

### 3-8. 문서

## 5. `manage.py race` — 눈으로 보는 도구 (준비 비용)

```
just race refund SEED-0003 --amount 30000   # 환불 제안 2개 동시
just race pay SEED-0004                      # 결제 2개 동시
just race approve <refund_id>                # 점주 확정 2개 동시
```

- 기본은 **in-process 결정적** 모드: 채점 테스트와 같은 Barrier 훅으로 스레드 2개가 서비스 함수를 직접 부른다. `db.sqlite3` 를 직접 만진다(`just reset-db` 로 되돌린다).
- `--http` 는 **확률적** 모드: 임시 `APIToken` 을 발급해(끝나면 삭제) `WORLD_URL`(기본 `http://127.0.0.1:8000`)에 요청 2개를 Barrier 로 동시에 쏜다. 창이 좁아 매번 겹치지 않으므로 `--rounds N`(기본 5)으로 반복하고 회차별 결과를 찍는다. 옆자리 학생과는 `WORLD_URL=http://<상대 IP>:8000` 로 각자 쏜다(`just run-shared` 가 `0.0.0.0` 바인드 + `WORLD_SHARED=1`).
- 출력은 두 줄 — `[A] 200 ALLOW  주문 SEED-0004 을(를) 결제 완료로 옮겼습니다.` / `[B] 409 DENY [ORDER-001@v1] …`. 판정은 하지 않는다 — 세계의 대답을 나란히 놓을 뿐이다.

## 6. `stages/05-경합.md` 뼈대 (4단계 지시서와 같은 형식)

1. **준비** — `just reset-db` · 4단계 "보장하지 않는 것" 표에서 5단계 행 4개를 다시 읽는다 · `cat agent/prompts/ai_staff.md` 4번.
2. **명령** — `just race refund SEED-0003 --amount 30000` → **승인 환불 2건**. `just race pay SEED-0004` → 200/409 (이건 버틴다). `just test 05` → 11개 중 8개 실패.
3. **의도적 실패** — 왜 결제는 버티고 환불은 못 버티는가: UPDATE 에는 `WHERE status=` 를 걸 행이 있고 INSERT 에는 없다. `services.propose_refund` 의 `filter().first()` 가 4단계에서 "콘솔이 걸러 줄 뿐"이라 했던 바로 그 줄이고, 두 스레드가 그 줄을 **같이** 통과한다(check-then-act). 그리고 `Refund.approve` 는 `save()` 다 — 승인 뒤 거부가 덮어쓴다.
4. **수정** — §3 순서대로(제약 → apply 뒤집기 → approve 계약 → 멱등키 입구 → 503). 각 항목에 "Django 가 준 자리" 표. `select_for_update` 실측 한 절: "잠갔다고 믿는 잠금".
5. **검증** — `just test 05` · `uv run pytest` · `just race …` 재실행 표(이사 전/후).
6. **이 단계의 한 문장** — *물어보고 쓰지 마라. 쓰고 나서 물어라.* (check-then-act → act-then-check. 유일 제약이 "물음"을 DB 에 맡긴다.)
7. **이 단계가 보장하지 않는 것** — 표:
   - 승인 시점 기한 재검사 — **정책으로 확정: 하지 않는다**(판정 시점 = 신청 시점). 이유: 기한은 사건의 성질이지 경합이 아니다. 바꾸려면 `REFUND-001@v2`.
   - 실제 잠금 실패 재현 — 채점 안 함(환경 의존). 503 은 **주입** 테스트로만. `IMMEDIATE`·`timeout` 은 빈도를 줄일 뿐 없애지 못한다.
   - 재고 마지막 1개를 두 **다른 주문**이 동시에 결제 — `stock__gte` 조건부 UPDATE(0단계 범용 법 + 4단계)가 막는다. 여기서는 실측하지 않는다(실접속 관찰 소재).
   - DENY 재전송 — 저장하지 않으므로 재판정. 7일 경계를 넘긴 재전송은 답이 바뀐다.
   - 멱등키 만료·정리 — 없다. 영원히 남는다.
   - 누가 재전송했는지·경합의 패자가 누구였는지 — 장부 없음(7단계). 소유권 스코핑(6단계).
8. **실접속으로 같은 것을 보기** — Claude 창 둘에서 "SEED-0003 을 3만원 환불해 줘"를 동시에 → 하나는 확정, 하나는 "이미 있다". 같은 창에서 두 번 → 두 번째 `outcome: REPLAYED`(도구가 `request_id` 를 줬을 때) 또는 `ALREADY`. `stages/live-실접속.md` (c) 표의 5단계 행 두 개를 "해결됨"으로 옮긴다.
9. **제출물** — `RULES.md` 행 1개 · 이사 비용 한 줄 · 설명 문항: **"UPDATE 경합과 INSERT 경합은 왜 다른 도구로 막는가? `select_for_update` 를 SQLite 에서 썼다면 무엇이 달라졌겠는가(답: 아무것도)."** · 마지막 한 줄.

## 8. 이 사양이 결정한 것 (재논의 시 여기서)

- 5단계의 법은 **하나**(`REFUND-003@v1`)이고 시행 면이 셋이다. 4단계처럼 "법 3개"가 아니다 — 세 면은 같은 문장의 세 경합 모양이다.

- `select_for_update` 는 구현하지 않고 **무효임을 실측**만 한다. PostgreSQL 이면 행 잠금이 된다는 말은 지시서에 한 줄만(8단계 전 외부 서비스 0).
- 콘솔(HTML) 카드는 추가하지 않는다. 눈으로 보는 도구는 `just race`.
- `live_server` 를 쓰지 않는다(§2).
- `WORLD_SHARED=1` 은 `ALLOWED_HOSTS` 개방 + `0.0.0.0` 바인드까지만. 학생별 계정·스코핑은 6단계.
