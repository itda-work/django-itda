# Postgres 실측 (2026-09-19) — 고치기 전 목록

근거: [차용-검토-itda-django-bridge.md](차용-검토-itda-django-bridge.md) §1-4·§5(순서 재조정의 4번). 이 문서는 **고치기 전**의 원문 목록이다 — 무엇을 고칠지는 목록이 정한다.

## 환경

- 컨테이너 `itda-django-pg` — `postgres:17-alpine`, 127.0.0.1:55433, db/user/pw `itda`. `examples/itda-django` 에서 `just pg-up`(없으면 만들고 `pg_isready` 까지 대기)·`just pg-down`.
- 설정 — 예시 `examples/itda-django/probes/pg_settings.py`(`config.settings` 상속), 패키지 `tests/pg_settings.py`(`tests.settings` 상속). 둘 다 `DATABASES` 를 **통째로** 교체한다 — SQLite 전용 `OPTIONS`(`transaction_mode`·`init_command`)와 `TEST.NAME`(파일 경로)이 따라오면 재는 것이 PG 가 아니라 설정 찌꺼기가 된다.
- 실행 — 예시 `just test-pg`·`just migrate-pg`, 루트 `just test-pg`. psycopg 는 `uv run --with 'psycopg[binary]'` 로만 들인다(의존성 추가 없음).
- 기준선(SQLite): 루트 70 passed · 예시 137 passed.

## 1. 먼저 — `ledger/0002` 에서 migrate 가 깨진다

`just migrate-pg`:

```
Applying ledger.0002_append_only_trigger...
django.db.utils.ProgrammingError: syntax error at or near "BEGIN"
LINE 4: BEGIN
```

`CREATE TRIGGER … BEGIN SELECT RAISE(ABORT, …); END;` 는 SQLite 문법이다. `RunSQL` 에 vendor 가드가 없어 PG 에서는 **migrate 자체가 실패**하고, 따라서 테스트 DB 도 만들어지지 않는다(예시 테스트 전량이 시작 전에 멈춘다). 차용 검토 §1-4 (a) 의 예상이 사실로 확인됐다.

나머지 목록을 얻으려고 **커밋하지 않은 임시 우회**를 썼다 — `0002` 의 `RunSQL` 을 `RunPython`(vendor 가 `sqlite` 일 때만 `CREATE`/`DROP` 실행)으로 바꿔 한 번 돌리고 `git checkout` 으로 되돌렸다. 그래서 아래 표의 `test_장부는_고칠_수_없다_DB_층` 실패는 **우회의 결과**(PG 에 트리거가 없음)다.

## 3. 읽을 것

- **5단계 경합 시험은 PG 에서 전부 통과했다.** SQLite 에서 "세계가 막는다" 를 보인 시험들이 PG 의 행 잠금·READ COMMITTED 아래에서도 같은 판정을 냈다 — 차용 검토 §1-4 (b)·(c) 의 걱정은 이 시험 범위에서는 깨지지 않았다. 다만 `select_for_update` 가 **실제로 잠근다**는 것은 시험이 없고, 그 빈자리가 SQLite 전용 실측 시험(`has_select_for_update is False`)으로 남아 있다.
- 패키지 `busy.is_lock_failure` 는 SQLite 오류 코드·메시지만 안다. PG 의 잠금 실패(`55P03`·`40P01`·`40001`)는 `OperationalError` 로 오지만 판별이 `False` 를 돌려 `ToolBusy` 가 아니라 `exception` 으로 번역된다 — 목록에는 시험이 없어 드러나지 않았다. 이것이 커밋 2 의 몫이다.

## 4. 패키지: 고친 뒤 (커밋 2 — `busy.is_lock_failure` vendor 인지)

`is_lock_failure` 가 원인 예외(또는 자신)의 `sqlstate` 를 먼저 본다 — `55P03`·`40P01`·`40001` 이면 잠금, 다른 `sqlstate` 면 메시지와 무관하게 잠금 아님, `sqlstate` 가 없으면 종전 SQLite 갈래 그대로. psycopg 는 임포트하지 않는다.

| 게이트 | 결과 |
|---|---|
| 루트 SQLite `uv run pytest` | 77 passed, 1 skipped(PG 실측 시험) |
| 루트 `ruff check` | 0건 |

## 5. 예시: 고친 뒤 (3·4단계 — `ledger/0002` vendor 분기 · 백엔드별 테스트 정리)

- **3단계(`ledger/0002`)** — `RunSQL` → `RunPython(forward, backward)`, `schema_editor.connection.vendor` 로 가른다. SQLite 는 종전 SQL 그대로(새 DB 의 `sqlite_master` 63행을 바꾸기 전·후 `cmp` — 바이트 단위 동일), PostgreSQL 은 `CREATE FUNCTION ledger_event_no_update() … RAISE EXCEPTION 'LEDGER-001@v1: 장부는 고치지 않는다' USING ERRCODE = '23000'` + `BEFORE UPDATE … FOR EACH ROW EXECUTE FUNCTION`, 그 밖의 vendor 는 아무것도 만들지 않는다.
  - ERRCODE 실측: `Event.objects.filter(pk=…).update(…)` → Django `IntegrityError`, 원인 `psycopg.errors.IntegrityConstraintViolation`, `sqlstate == '23000'`, 메시지 첫 줄 `LEDGER-001@v1: 장부는 고치지 않는다`. `23000` 그대로 맞았다(다른 코드를 찾을 필요 없음).
  - 역방향 실측: `migrate ledger 0001` → `pg_trigger`·`pg_proc` 의 `ledger_event_no_update` 0건, 다시 `migrate` → 1건.
  - `DELETE FROM ledger_event` 는 PG 에서도 막지 않는다(사양 §2-1 결정 유지 — 테스트 flush). 실측으로 지워짐을 확인. PG 에서는 `REVOKE DELETE`·`BEFORE DELETE` 트리거로 닫을 수 있다(운영 소재).
  - 계정 삭제 — `test_장부에_남은_계정은_지울_수_없다` 가 PG 에서도 `ProtectedError`(0003 의 `PROTECT`).
- **4단계(테스트)** — SQLite 전용 실측 3건에 `skipif(connection.vendor != 'sqlite')`(본문·단언 그대로). PG 전용 실측 2건은 채점표 밖 `examples/itda-django/tests/pg_probe.py`(PG 가 아니면 모듈 skip, `python_files` 에 `pg_*.py`).
  1. `select_for_update(nowait=True)` — 스레드가 행을 쥔 동안 두 번째 연결이 `OperationalError`, 원인 `sqlstate == '55P03'`, `is_lock_failure` True. 풀린 뒤 같은 질의는 통과.
  2. 같은 상품(재고 20)을 담은 서로 다른 주문 둘(수량 2·3)을 Barrier 로 동시에 `mark_paid` → 둘 다 결제, `stock.deducted` 두 줄이 겹치지 않고 이어지며(20→18→15 또는 20→17→15) 끝값이 실제 재고 15. **시험이 실패할 수 있음 확인**: `mark_paid` 를 재조회 전(스냅샷 `item.product.stock`)으로 임시로 되돌려 PG 에서 3회 → 3회 모두 `{'stock': 20} == {'stock': 18}` 로 실패(되돌림은 커밋하지 않음).

|---|---|
| 예시 SQLite `uv run pytest` | 137 passed, 2 skipped(`pg_probe.py` 2) |
| 예시 PG `just test-pg` | **136 passed, 3 skipped(SQLite 전용 실측 3), 0 failed** |
