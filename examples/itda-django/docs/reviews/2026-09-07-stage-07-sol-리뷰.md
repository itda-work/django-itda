  확인된 보장과 사양 자체의 오류

  - Refund.apply()의 _resolve_collision은 atomic 바깥에서 실행된다. 실패한 생성 시도의 이벤트는
    롤백되고, 기존 환불을 반환하면서 새 이벤트를 만들지 않는다. 별도 무결성 오류가 기존 행으로
    가려질 수 있다는 한정은 5단계 반영 결정대로 이미 공개돼 있다.

  - Order.save() 실패를 자동 승인 경로에 주입한 결과는 환불 0건 / 추가 이벤트 0건 / 주문 paid였
    다. 이 롤백 보장은 정상이다.

  - 시작 사본에서 manage.py race pay SEED-0004와 manage.py ledger를 실제 실행하니 결제·차감 이벤
    트가 각각 2건, 완료 상태에서는 결제 1건이었다. 의도적 실패 화면과 4단계 rowcount 버그의 연결
    은 재현된다.

  - 문맥 실측은 sync_to_async(thread_sensitive=True)에서 유지됐다. 새 threading.Thread와 bind 범
    위를 빠져나간 뒤 실행한 on_commit에서는 ('', 'shell', None)이었다. 현재 race 명령의 shell 표
    시는 맞지만, 문맥이 모든 지연 작업에 자동 전파된다는 보장은 없다.

  - Toolset.call은 권한 거부 시 본문을 실행하지 않고, busy·예외 처리 전에 bind를 해제한다. 호출
    기록은 명시적인 base 값을 사용하므로 이 갈래에서 잘못된 문맥을 기록하는 결함은 확인되지 않았
    다. X-Request-ID의 위조·재사용 위험은 이미 정직하게 공개했다.

  - 패키지 내부 fastmcp 임포트는 어댑터에 한정돼 있고 새 문맥 API도 첫 사용자가 소비한다. 다만
    CallContext.actor는 현재 도메인 소비자가 읽지 않는 여분이다. 장부 actor는 명시 인자를 사용한
    다.

  사양에서 고쳐야 할 설명은 다음과 같다.

  - §9의 SQLite 스냅샷 안전 판단은 오류다. 발견 1은 경쟁 트랜잭션 없이 재현된다.
  - SET_NULL과 무조건 갱신 금지는 동시에 성립하지 않는다.
  - “contract부터”는 expand 후 backfill만 생략한다는 뜻으로 명확히 해야 한다. 아직 없는 필드를
    참조하는 제약만 추가하는 절차와 구별해야 한다. 실제 기존 행이 있는 임시 DB에서는 backfill 생
    략 시 CHECK constraint failed: order_paid_has_paid_at, 정상 적용 시 paid_at == created_at을
    확인했다.

  - “두 UPDATE로 나누면 제약이 지키는 것이 없어진다”는 설명은 반대다. 활성 제약이 첫 번째 잘못된
    상태 UPDATE를 거절하기 때문에 같은 문장에서 채워야 한다.

  - 취소 주문을 무조건 backfill하라는 근거는 없다. Refund.decided_at은 환불 결정 시각이지 결제
    시각이 아니다. 현재 환불 판정은 pending 주문도 허용하므로 승인된 환불만으로 결제를 증명할 수
    도 없다. 다만 과거 실접속 기록으로 일부 시드 주문의 결제 상태를 알 수 있으므로 “영영 모름”보
    다는 “현재 DB만으로 일괄 복원하지 않음”이 정확하다.

  - 설계서의 음수 재고 실습 정정과 REFUND-001@v2 보류는 코드와 일치한다.
