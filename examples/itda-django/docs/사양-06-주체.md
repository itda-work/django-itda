- **지위**: 빌더(`app-builder`) 지시서 겸 설계 결정 기록. 학생용 지시서는 `stages/06-주체.md`(빌더가 이 사양에서 만든다).
- **선행 정본**: `docs/단계별-설계.md` §3 6단계 행(이 사양이 그 행을 **정정**한다 — §8) · `stages/05-경합.md` "이 단계가 보장하지 않는 것" · `stages/live-실접속.md` (c) 표 · `docs/사양-05-경합.md`(형식·규율).
- **결정 근거**: 마스터 논의 2026-09-07 — 결제의 확정자는 점주가 아니라 **고객**이다(관통 문장의 두 번째 사람). 결제 링크는 **1시간** 만료. 만료 구현은 Django `django.contrib.auth.tokens.PasswordResetTokenGenerator` 를 빌린다(원문 검토 완료 — §2).

## 0. 한 문장

> 지금까지 이 세계의 사람은 점주 하나였다. 결제는 돈을 내는 사람의 확정이라 AI 직원이 대신 누를 일이 아니다 —
> **고객이 세계에 처음 들어온다.** 사람이 둘이 되는 순간 "누구의 것인가" 가 법이 되고, 링크로 들어오는 순간 "언제까지인가" 가 법이 된다.

관통 문장(제안은 AI, 판정은 세계, 확정은 사람)에서 **확정하는 사람이 둘**이 된다. 환불은 점주가, 결제는 고객이 확정한다. 격상(ESCALATE)의 두 번째 사례이고, 승인 핸들이 "admin 에서 누른다" 에서 "URL 을 연다" 로 일반화된다.

## 1. 켜는 법 — 둘 (예외 근거 포함)

| ID | 원문(점주) | 시행 형식 | 코드 위치 |
|---|---|---|---|
| `PAY-001@v1` | **결제는 네가 하지 마라. 고객에게 결제 링크를 안내하고 고객이 직접 결제하게 하라. 링크는 발급 후 1시간 안에만 유효하다.** | 발급 판정(대기 상태에서만) + **서명 토큰 만료**(프레임워크 법 빌림) + 전이 계약(4단계 그대로) | `orders/services.py:issue_payment_link` · `orders/tokens.py:PaymentLinkTokenGenerator` · `orders/views.py:pay_page` · `Order.mark_paid` |
| `SCOPE-001@v1` | **고객의 주문은 그 고객에게만 보여 줘라.** | 쿼리 스코핑 — `get_object_or_404(Order, pk=pk, user=request.user)` → 남의 것은 **404** | `orders/views.py:pay_page` |

두 원문은 시작 상태에서 `agent/prompts/ai_staff.md` "반드시 지켜야 할 것" **5·6번**으로 먼저 들어간다(4·5단계와 같은 이사 구조). 완료 상태에서 이사 표시를 단다. **6번은 부분 이사다** — 고객 문(결제 페이지)에서만 지켜지고, AI 직원의 문(`list_orders`)에서는 여전히 모든 고객의 주문이 보인다. 표시는 `→ 코드로 이사됨 (SCOPE-001@v1, 고객 문에 한해 — AI 직원 문은 미이사)` 로 쓴다. 이 "부분" 이 8단계 부채 리포트의 첫 실물이다.

**한 단계 = 법 하나 규율의 예외.** 4단계가 "단위 = 프롬프트 파일 하나" 로 셋을 허용했듯, 6단계는 **"단위 = 결제 페이지 하나"** 다. 두 법은 같은 화면의 같은 요청에서 태어난다 — 링크를 연 사람이 **누구**인가(SCOPE), **언제** 열었는가(PAY). 하나만 켜면 화면이 반쪽이다.

`PAY-001` 의 시행 면이 셋인 이유(5단계 `REFUND-003` 과 같은 구조):

| 무엇을 막나 | 막는 것 | Django 가 준 자리 |
|---|---|---|
| AI 직원이 결제를 완료시킨다 | AI 의 문에서는 **링크 발급까지**. `mark_paid` 를 부르는 곳이 고객 페이지 뿐이 된다 | 권한이 아니라 **경로** — `pay_order` 도구·API 가 `issue_payment_link` 를 부른다 |
| 오래된 링크로 세계를 움직인다 | 토큰 타임스탬프 + 1시간 | `PasswordResetTokenGenerator.check_token` 의 시간 비교 |
| 결제된 주문의 링크가 살아 있다 | 토큰 해시에 **주문 상태**를 섞는다 — 상태가 바뀌면 같은 토큰이 스스로 죽는다 | `_make_hash_value` (비밀번호 해시가 하던 역할을 `order.status` 가 한다) |

**만료는 이중 결제를 막는 장치가 아니다.** 그것은 4단계 `ORDER-001` 의 몫이고 그대로다. 토큰이 먼저 닫고, 계약이 마지막에 지킨다 — 두 겹이다. 지시서에 이 문장을 그대로 쓴다.

## 2. 설계 — 결제 링크 (검토한 Django 원문 기준)

`django/contrib/auth/tokens.py` 에서 빌리는 것과 빌리지 않는 것.

### 빌린다

- `PasswordResetTokenGenerator` 서브클래스 `orders/tokens.py:PaymentLinkTokenGenerator`.
  - `key_salt = 'orders.tokens.PaymentLinkTokenGenerator'` — **반드시 따로 준다.** 부모 salt 를 쓰면 비밀번호 토큰과 결제 토큰이 같은 키 공간에 섞인다.
  - `_make_hash_value(order, timestamp)` → `f'{order.pk}{order.status}{order.total_amount}{order.user_id}{timestamp}'`. **`updated_at` 을 넣지 않는다** — 어떤 `save()` 도 링크를 죽여 버린다. "바뀌면 결제 조건이 달라지는 것" 만 섞는다.
  - `check_token(order, token)` — 부모가 `settings.PASSWORD_RESET_TIMEOUT` 을 박아 두어 **이 메서드만 다시 쓴다**(원문 그대로, 설정 이름만 `self.timeout`). 나머지(`make_token`·`_make_token_with_timestamp`·`_num_seconds`·`_now`)는 상속.
  - `timeout` 프로퍼티: `getattr(settings, 'PAYMENT_LINK_TIMEOUT', None) or rules.PAY_LINK_TIMEOUT`. 법의 숫자는 `orders/rules.py:PAY_LINK_TIMEOUT = 60 * 60`(버전을 붙이는 자리), settings 는 **관찰용 노브**만(`config/settings.py`: 환경변수 `PAYMENT_LINK_TIMEOUT` 이 있을 때만 설정). 지시서에 "1시간을 기다리지 않는다 — `PAYMENT_LINK_TIMEOUT=5 just run`" 으로 쓴다.
  - `_now()` 는 테스트에서 `mock.patch.object(PaymentLinkTokenGenerator, '_now')` 로 시계를 돌린다(원문 주석 "Used for mocking in tests" 그대로).
  - 모듈 인스턴스 `payment_token = PaymentLinkTokenGenerator()`.
- URL 모양: `/pay/<int:pk>/<str:token>/`. 비밀번호 흐름의 `uidb64` 자리에 주문 pk.

### 빌리지 않는다

- `PasswordResetConfirmView` 의 세션 리다이렉트(토큰을 세션에 옮기고 `set-password` URL 로 바꾸는 Referer 누출 방지). 결제 페이지에는 외부 링크가 없고 6단계 diff 를 키운다. "보장하지 않는 것" 표에 8단계 운영 소재로 적는다.
- `default_token_generator` 인스턴스 공유.

### 결제 페이지 — 세 질문을 순서대로

`orders/views.py:pay_page(request, pk, token)`, `@login_required(login_url='accounts:login')`:

1. **누구인가** — `get_object_or_404(Order, pk=pk, user=request.user)`. 남의 주문은 404 (`SCOPE-001`). 403 이 아니다 — "있는데 못 본다" 가 아니라 "네 세계에는 없다".
2. **언제인가** — `payment_token.check_token(order, token)` 이 거짓이면 **409** + `Verdict(DENY, [PAY_001])`. reason: `'PAY-001@v1: 결제 링크가 닫혔다 — 1시간이 지났거나 주문 상태가 바뀌었다. ' + RULE_TEXTS[PAY_001]`. alternatives 는 **상태를 보고** 고른다(없는 길을 적지 않는다): 주문이 아직 `pending` 이면 `['AI 직원에게 새 결제 링크를 요청한다']`, 아니면 `['주문 내역에서 현재 상태를 확인한다']`.
3. **결제** — GET 은 주문 요약(상품·수량·금액·`expires_at`)과 결제 버튼. POST 는 1·2 를 다시 지나고 `services.pay_order(order)` → ALLOW 면 완료 화면(200), DENY 면 판정 화면(409, `ORDER-001`). 결제 페이지는 경합의 자리이기도 하다 — 두 탭에서 동시에 누르면 토큰은 둘 다 통과하고 `mark_paid` 가 하나를 거른다.

### 링크 발급 — AI 의 문

`orders/services.py:issue_payment_link(actor, order) -> (Verdict, dict | None)`:

- `order.status != PENDING` → `Verdict(DENY, [ORDER_001], reason=f'{ORDER_001}: 결제 대기 상태가 아니다 — 링크를 발급하지 않는다. {RULE_TEXTS[ORDER_001]}', alternatives=['주문 내역에서 이 주문의 현재 상태를 조회한다'])`, payment `None`. `mark_paid` 의 문장과 같은 규칙 ID, 다른 자리.
- 아니면 `Verdict(ESCALATE, [PAY_001], reason=f'{PAY_001}: 결제는 고객이 한다. 결제 링크를 발급했다 — 1시간 안에 고객이 결제해야 한다. {RULE_TEXTS[PAY_001]}', alternatives=['고객에게 링크를 안내하고 결제 완료를 주문 조회로 확인한다'])` + `{'url': <절대 URL>, 'expires_at': <ISO>}`. 절대 URL 은 `settings.WORLD_PUBLIC_URL`(기본 `http://127.0.0.1:8000`) + `reverse('pay', args=[order.pk, payment_token.make_token(order)])`. `expires_at = timezone.now() + timedelta(seconds=payment_token.timeout)` — **정보용**이다. 정본은 토큰이다.
- 세계에 **아무것도 쓰지 않는다**(무상태). 누가 언제 링크를 발급했는지, 어떤 링크로 결제됐는지는 안 남는다 → 7단계 장부의 시작 결함(보장하지 않는 것 표).

### 문마다

| 문 | 변경 |
|---|---|
| API `POST /api/orders/<pk>/pay/` | `issue_payment_link` 로. ESCALATE → **202**, `outcome: QUEUED`, `payment: {url, expires_at}`, `order`(아직 pending). DENY → 409. 200 은 더 이상 없다 |
| 패키지 도구 `agent/live/tools.py:pay_order` | `handle_tool='get_order', handle_subject='order'`. 반환 objects 에 `'payment': {...}` 와 **`'handle': {'url', 'expires_at'}`**(§5 패키지 변경 — 자동 핸들 위에 병합). docstring: "결제를 완료시키지 않는다. 링크를 발급한다. `handle.url` 을 고객에게 안내하고 `get_order` 로 확인하라" |
| 임시 HTTP 서버 `agent/live/mcp_server.py` | **손대지 않는다**(8단계에서 대체). 202 를 `_escalated` 가 `refund` 기준으로 조립하므로 `refund_id: null` 이 나온다 — 발견 1 의 재확인이고, `live-실접속.md` (a') 표에 한 줄 |
| 콘솔 | 카드 **⑦ `pay-link`** 신설: ① 이 접수한 alice 의 최신 `pending` 주문에 링크 발급 → ESCALATE, 콘솔에 URL 과 만료 시각 표시(`agent/denied.html` 이 아니라 `agent/console.html` 의 메시지 영역 — `messages.info`). 카드 **⑥ `repay-paid`** 는 `_repay` 가 `issue_payment_link(SEED-0002)` 를 부르게 바뀌고 문구는 "결제가 안 잡힌 것 같아 링크를 다시 발급" → DENY `ORDER-001`(같은 교훈, 같은 규칙 ID). 카드 ① 의 `expect` 에 "결제는 고객이 한다 — ⑦ 에서 링크를 발급한다" 한 줄 |
| 고객 로그인 | `accounts/urls.py`(신규) `login/`·`logout/` (`LoginView`·`LogoutView`, 템플릿 `templates/accounts/login.html` 최소) + `config/urls.py` `path('accounts/', include('accounts.urls'))`. 콘솔 로그인 `/agent/login/` 은 AI 직원용으로 그대로. `LOGIN_URL` 은 바꾸지 않는다(콘솔 뷰가 쓴다) — `pay_page` 만 `login_url` 을 명시 |
| 403 분리(`config/views.py`) | `/pay/`·`/accounts/` 는 사람 페이지 → 일반 403. `AGENT_PREFIXES` 무변경(주석 "`/orders/` 에 사람 전용 페이지가 없다" 는 여전히 참 — 결제 페이지는 `/pay/`) |
| `manage.py race` | `pay` 모드의 `--http` 는 **뺀다**(결제가 고객 세션이 되어 토큰 API 로 못 쏜다). in-process `race pay` 는 `services.pay_order` 로 그대로. `--http pay` 를 주면 "6단계부터 결제는 고객 세션 — refund/approve 만 --http" 로 종료 |

## 4. 시작 상태(`stage-06-start`) — 준비 비용 (크다 — 의도)

> 시드 사실: SEED-0004(결제 대기, 한정판 1개)의 주문자는 **bob** 이다. 채점표의 '주문자' 는 bob, '남' 은 alice. 콘솔 ⑦ 이 링크를 만드는 주문은 ① 이 접수한 **alice** 의 새 주문이라 지시서 절차의 침입자는 bob 이다.

5단계 done 위에 얹는다. 준비가 큰 이유는 **고객의 문이 통째로 새로 생기기** 때문이다. 학생 diff 가 아니라 교재 비용이다(설계 §3-2 의 두 축 분리 그대로 기록).

1. 고객 로그인(`accounts/urls.py`, 템플릿).
2. 결제 페이지 `/pay/<int:pk>/` — **결함 둘을 심는다**: `get_object_or_404(Order, pk=pk)`(주문자 검사 없음 — 로그인만 하면 누구 주문이든 열리고 결제된다), 토큰 없음(링크가 영원히 산다). 템플릿 `orders/pay.html`·`orders/pay_result.html`.
3. `services.issue_payment_link` — 시작 상태는 토큰 없는 URL 을 돌려주고 `expires_at: null`. 판정은 완료 상태와 같은 모양(ESCALATE / DENY)이되 ESCALATE 의 `rule_ids` 는 `[]`(법이 아직 없다).
4. API·도구·콘솔 ⑦·⑥ 변경(§2 "문마다") — 시작 상태에서 이미 "결제는 고객이" 다. 프롬프트 5·6번(이사 표시 없이).
5. `tests/stage_05_contention.py::test_동시_결제_두_개_중_하나만_통과한다_HTTP` — API 가 202 를 주게 되어 **결제 페이지 POST 로 옮긴다**(SEED-0004 주문자 **bob** 세션 `Client()` 2개, `Order.mark_paid` 에 Barrier, 결과 `{200, 409}`, 재고 1→0). 파일 docstring 에 "6단계에서 결제 주체가 고객으로 바뀌어 옮김(2026-09-07). 태그 `stage-05-*` 는 그대로" 주석. `tests/live_api.py`·`tests/live_tools.py` 의 결제 관련 단언은 202/ESCALATE·`payment.url`·`handle.check_tool == 'get_order'` 로 갱신(회귀 테스트이지 채점표가 아니다).
6. `manage.py race` `--http pay` 제거(§2).
7. `tests/stage_06_subject.py` 채점표(아래). `stages/06-주체.md` 지시서 뼈대(§6). `stages/README.md` 6단계 행에 `stage-06-start`.
8. `config/settings.py`: `WORLD_PUBLIC_URL`, `PAYMENT_LINK_TIMEOUT` 노브(환경변수 있을 때만).

## 8. 이 사양이 결정한 것 (재논의 시 여기서)

- **6단계의 법은 둘**(`PAY-001@v1`·`SCOPE-001@v1`), 단위는 "결제 페이지 하나". 4단계 예외와 같은 격.
- **결제의 확정자는 고객**이다. AI 직원의 문에서는 링크 발급까지. `Order.mark_paid` 를 부르는 곳은 결제 페이지 뿐(그리고 shell — 우회 가능 경로로 `RULES.md` 에 적는다).
- 만료 구현은 **`PasswordResetTokenGenerator` 서브클래스**(무상태·상태 결합 무효화). `signing.TimestampSigner` 와 `PaymentLink` 모델은 기각 — 전자는 상태 결합이 없고, 후자는 7단계 장부를 앞당긴다.
- 만료 시간의 정본은 `orders/rules.py:PAY_LINK_TIMEOUT = 3600`. settings 노브는 관찰용이다.
- **설계서 §3 6단계 행의 정정**: "상품 설명에 주입 페이로드 seed → fixture AI 가 지시를 따라 `/api/orders/` 호출 → 자기 주문만" 축은 6단계에서 **뺀다.** 이유: 그 축의 주체는 "AI 직원이 지금 누구를 대신하는가"(대행 스코핑)인데, 이 세계의 AI 직원은 가게 직원이라 모든 주문을 보는 것이 자리에 맞고, 대화별 대행 주체는 아직 세계에 없다. 6단계의 주체는 **고객**이고, 그 첫 문이 결제 페이지다. 대행 스코핑과 주입 재현은 "보장하지 않는 것" 표에 남겨 8단계 부채 리포트의 입력으로 이월한다(설계서 §3 행 아래에 정정 블록으로 기록. 원문은 지우지 않는다).
- 임시 HTTP 서버는 계속 손대지 않는다.
- 결제 페이지의 소유권 실패는 **404** 다(403 이 아니다).

- **`issue_payment_link(actor, order)` 의 `actor`** — 사양이 시그니처만 정하고 용도를 안 정했다. 정정: 지금은 쓰지 않는 인자이고, **7단계 장부("누가 링크를 발급했나")의 자리**로 미리 뚫어 둔 것이다. 함수 docstring 에 그 한 줄을 적는다(수정 라운드).

검증이 지적한 **낮은 우려** 셋 중 둘은 수정 라운드에서 고친다 — `stages/README.md` 비용표 재현 명령의 `'tests/*'` pathspec(루트 기준이라 예시 프로젝트 채점표를 못 잡는다 → `'*/tests/*'`), `orders/tokens.py:check_token` docstring 의 "원문 그대로"(구현은 `<=` 로 동치 변형 — 원문 `>` 와의 관계를 명시). 나머지 하나(`expires_at(token)` 표시의 시스템 TZ 의존)는 표시 전용이라 8단계 배포 소재로 "보장하지 않는 것" 표에 한 줄 더한다.
