## 0. 한 문장

> 지금까지 세계는 **움직이기만** 했다. 누가 언제 어느 문으로 무엇을 근거로 움직였는지는 `decided_via` 한 칸과 `LogEntry` 0건이 전부다.
> 이번 법은 "세계가 움직인 사실은 세계와 같은 트랜잭션에서 장부에 남는다" 이고, 장부는 **고쳐 쓸 수 없다.**

관통 문장에 마지막 한 겹: **판정은 세계, 확정은 사람 — 그리고 그 둘의 기록은 세계 자신이 남긴다.** 도구면의 궤적(`ToolCall`, "누가 무엇을 시켰나")과 도메인 장부(`ledger.Event`, "세계가 무엇으로 바뀌었나")가 `call_id` 로 잇닿아, 제안 → 판정 → 확정이 하나의 사건 사슬이 된다.

## 1. 켜는 법 — 하나 (+ 범용 제약 하나)

| ID | 원문(점주) | 시행 형식 | 코드 위치 |
|---|---|---|---|

원문은 시작 상태에서 `agent/prompts/ai_staff.md` "반드시 지켜야 할 것" **7번**으로 먼저 들어간다(이사 구조 그대로). 완료 상태에서 `→ 코드로 이사됨 (LEDGER-001@v1, ledger/models.py:Event.record — 전이 메서드 안 · DB 트리거)` 표시.

**범용 제약 하나가 같이 켜진다 — 법이 아니라 원가계산 실습이다.** `Order.paid_at`: 결제 완료 이후 상태(`paid`·`shipping`·`completed`)의 주문은 결제 시각을 가진다(`CheckConstraint`). 0단계의 `PositiveIntegerField` 처럼 점주가 말한 문장이 아니므로 `RULES.md` 행이 **아니다.** 이것이 켜지는 과정(expand → backfill → contract 3커밋)이 안건2 ③이 확정한 "선언 1줄 + migration + **기존 데이터의 법 위반 정리**" 실습이다.

**한 단계 = 법 하나** 규율 안이다. `paid_at` 제약은 법이 아니고, `REFUND-001@v2`(결제일 = `paid_at`)는 **이번에 하지 않는다**(§8).

## 2. 설계

### 2-1. 장부 — `ledger.Event`

append-only 이벤트. **세계가 실제로 바뀐 사실**만 적는다. 거부(DENY)·재전송(REPLAYED)·기존 건 응답(ALREADY)은 세계를 바꾸지 않았으므로 여기 없다 — 그 호출은 도구면 궤적(`ToolCall`)의 몫이다(루트 `docs/설계.md` §6).

| 필드 | 형 | 뜻 |
|---|---|---|
| `at` | `DateTimeField` | 기록 시각(`timezone.now()`, `auto_now_add` 아님 — 전이 메서드가 정한 시각과 같아야 한다) |
| `door` | `CharField(20)` choices `mcp/api/console/admin/customer/shell` | **어느 문으로** 들어온 요청이 만든 사실인가. 발견 3 의 답 — admin 경로도 여기 남는다 |
| `call_id` | `CharField(32, blank, db_index)` | 상관 ID. MCP 면 `ToolCall.call_id` 와 같고, HTTP 면 요청 ID, shell 이면 빈 값 |
| `actor` | FK `AUTH_USER_MODEL` null `SET_NULL` | 누가. 규칙 자동 확정은 `None` |
| `actor_label` | `CharField(50, blank)` | `username` 스냅샷 — `SET_NULL` 뒤에도 이름은 남는다 |
| `subject_type` / `subject_id` | FK `ContentType` / `PositiveIntegerField` | 무엇이 (`GenericForeignKey subject`) |
| `subject_label` | `CharField(100)` | `str(subject)` 스냅샷(주문번호 등) |
| `transition` | `CharField(50)` | `order.placed` · `order.paid` · `order.cancelled` · `stock.deducted` · `refund.proposed` · `refund.approved` · `refund.rejected` · `payment_link.issued` |
| `kind` | `CharField(20)` | 그 사실을 만든 판정 — `ALLOW` / `ESCALATE` (DENY 는 없다) |
| `rule_ids` | `JSONField(list)` | **판정 각인** `decisive_rules[]` — 어떤 규칙이 이 사실을 허락·격상했나 |
| `reason` | `TextField(blank)` | **세계의 판정 문장**. 고객·모델이 쓴 원문(환불 사유·제안 문구)은 넣지 않는다 — 장부가 오염 벡터가 된다(포스팅 점검 ⚠) |
| `before` / `after` | `JSONField(dict)` | 상태 스냅샷(`{'status': 'pending'}` → `{'status': 'paid', 'paid_at': …}`) |

- `Event.record(*, subject, transition, kind, rule_ids=(), reason='', before=None, after=None, actor=None)` — `door`·`call_id` 는 인자로 받지 않고 **`django_itda.context.current_call()` 에서 읽는다**(§2-3). 반환 `Event`.
- **append-only, 모델 층**: `save()` 는 `pk` 가 있으면 `LedgerImmutable`(자체 예외, `IntegrityError` 서브클래스 아님)을 던진다. `delete()`·`QuerySet.delete()` 도 같다(커스텀 `QuerySet`). `QuerySet.update()` 는 모델 층이 못 막는다 — 그래서 DB 층이 있다.
- **append-only, DB 층**: `ledger/migrations/0002_append_only_trigger.py` — `RunSQL` 로 `CREATE TRIGGER ledger_event_no_update BEFORE UPDATE ON ledger_event BEGIN SELECT RAISE(ABORT, 'LEDGER-001@v1: 장부는 고치지 않는다'); END;` (reverse: `DROP TRIGGER`). `RAISE(ABORT)` 는 `SQLITE_CONSTRAINT` 라 Django `IntegrityError` 로 올라온다. **DELETE 트리거는 걸지 않는다** — Django 테스트 DB flush 가 `DELETE FROM` 을 쓰므로 걸면 teardown 이 깨진다. 삭제는 모델 층만 막고 "우회 가능 경로" 열에 정직하게 적는다(8단계: DB 역할 권한으로).
- `Meta.ordering = ['at', 'id']`, verbose_name '장부'. admin `EventAdmin` 읽기 전용(6단계 `ToolCallAdmin` 과 같은 모양), list `at·door·actor_label·transition·subject_label·kind`, 필터 `door·transition·kind`, 검색 `call_id·subject_label`. `date_hierarchy='at'`.
- 점주 그룹에 `ledger.view_event` 시드(`seed_world`). AI 직원에겐 주지 않는다(8단계 — 자기 궤적).

### 2-2. 어디서 적는가 — 전이 메서드 안, 사실 뒤

| 사실 | 적는 자리 | before → after | kind / rule_ids |
|---|---|---|---|
| `order.placed` | `services.intake_order` 의 `atomic` 안, 생성 뒤 | `{}` → `{'status':'pending','total_amount':…}` | ALLOW / `[]` |
| `order.paid` | `Order.mark_paid(actor)` 의 `atomic` 안, **rowcount 확인 뒤·재고 차감 뒤** | `{'status':'pending'}` → `{'status':'paid','paid_at':ISO}` | ALLOW / `[]` |
| `stock.deducted` | `mark_paid` 의 품목 루프, **`updated` 확인 뒤** 품목마다 | `{'stock': n}` → `{'stock': n-q}` (subject = `Product`) | ALLOW / `[]` |
| `refund.proposed` | `Refund.apply` 의 `atomic` 안, `create` 뒤 | `{}` → `{'status':'proposed','amount':…}` | verdict.kind / verdict.rule_ids(**각인**) |
| `refund.approved` + `order.cancelled` | `Refund.approve` 의 `atomic` 안, rowcount 뒤 — 이벤트 **둘**, 같은 `call_id` | refund `{'status':'proposed'}`→`{'status':'approved','decided_via':…}` · order `{'status':…}`→`{'status':'cancelled'}` | ALLOW / `[]` (규칙 확정이면 `refund.proposed` 의 각인이 앞 행에 있다) |
| `refund.rejected` | `Refund.reject` 의 `atomic` 안, rowcount 뒤 | `{'status':'proposed'}`→`{'status':'rejected'}` | ALLOW / `[]` |
| `payment_link.issued` | `services.issue_payment_link`, **ESCALATE 일 때만** | `{}` → `{'expires_at': ISO}` | ESCALATE / `[PAY-001@v1]` — 6단계의 `actor` 인자가 여기서 쓰인다 |

규칙: **거부되면 아무것도 적지 않는다.** 롤백되면 이벤트도 롤백된다(같은 트랜잭션). 재전송·기존 건 응답은 새 사실이 아니라 새 행이 없다.

`Order.mark_paid()` 는 **`mark_paid(actor)`** 가 된다(4단계 표의 "전이에 actor 없음"). 부르는 자리 셋 — `services.pay_order(actor, order)`(결제 페이지가 `request.user` 를 넘긴다), `race pay`(주문자를 넘긴다), 테스트. `paid_at` 은 상태 UPDATE 와 **같은 문장**에서 채운다(`update(status=PAID, paid_at=now)`).

### 2-3. 문과 상관 ID — django-itda v0.2 (선행 커밋)

도메인 코드는 요청도 도구도 모른다. "어느 문·어느 호출" 은 **문이 열릴 때 문맥에 묶고**, 장부가 읽는다.

- `django_itda/context.py` — `contextvars.ContextVar` 하나. `bind_call(call_id, via, actor=None)` 컨텍스트 매니저, `current_call() -> CallContext(call_id, via, actor)`(묶인 것이 없으면 `CallContext('', 'shell', None)`).
- `Toolset.call` — 권한 검사 뒤 `spec.fn` 실행을 `bind_call(call_id, via, actor)` 로 감싼다. 도구가 부른 서비스·모델이 장부를 적으면 `ToolCall.call_id` 와 같은 값이 실린다 — **도구면 궤적과 도메인 장부가 잇닿는 지점.**
- `django_itda/middleware.py:CallContextMiddleware` — 요청마다 `call_id = X-Request-ID 헤더(32자 이내 hex/uuid 만) 또는 uuid4().hex`, `via = settings.ITDA['VIA']` 접두사 표에서(첫 일치, 없으면 `'web'`), `actor` 는 묶지 않는다(토큰 인증이 뷰 데코레이터 안에서 일어나 미들웨어 시점엔 모른다 — 장부는 actor 를 명시 인자로 받는다). 응답 헤더 `X-Call-ID` 로 되돌려 준다(관찰용). `ATOMIC_REQUESTS` 와 무관.
- itda-django 배선: `MIDDLEWARE` 에 `WorldBusyMiddleware` 다음, `ITDA['VIA'] = {'/api/': 'api', '/admin/': 'admin', '/agent/': 'console', '/orders/': 'console', '/pay/': 'customer'}`.
- 패키지 문서·테스트: `docs/설계.md` §6 에 "잇는 방법" 한 절, §11 표 행. `tests/test_context.py`(bind/current 기본값·중첩·스레드 격리는 `sync_to_async(thread_sensitive=True)` 경로에서 유지되는가), `tests/test_middleware.py`(헤더 있음/없음·접두사·기본 `web`·응답 헤더). `__version__='0.2.0'`.

### 2-4. `paid_at` — expand → backfill → contract (완료 상태의 3 마이그레이션)

| 커밋 안 순서 | 마이그레이션 | 내용 | 실패하는 조건 |
|---|---|---|---|
| expand | `orders/000N_order_paid_at.py` | `paid_at = DateTimeField(null=True, blank=True)` | 없음 |
| backfill | `orders/000N+1_backfill_paid_at.py` | `RunPython`: `status in (paid, shipping, completed)` 이고 `paid_at IS NULL` 인 행에 `paid_at = created_at`(4단계 교육상 가정을 **데이터로** 고정). `cancelled` 는 건드리지 않는다 — 결제 뒤 취소인지 결제 전 취소인지 **장부가 없던 시절엔 알 수 없다.** 그 모름을 그대로 둔다 | 없음 |
| contract | `orders/000N+2_order_paid_has_paid_at.py` | `CheckConstraint(check=Q(status__in=['pending','cancelled']) \| Q(paid_at__isnull=False), name='order_paid_has_paid_at')` | backfill 없이 적용하면 시드 주문(SEED-0001·0002·0003)에서 `IntegrityError` — **이것이 원가계산이다.** 지시서는 학생에게 contract 를 먼저 써 보게 한다 |

지시서 절 "원가계산": 선언 한 줄(`CheckConstraint`)의 진짜 비용은 **이미 있는 행**이다. 4단계 표가 "`created_at` 을 결제일로 쓰는 가정 위에 서 있다" 고 적어 둔 그 가정이, 여기서 데이터가 된다.

## 8. 이 사양이 결정한 것 (재논의 시 여기서)

- **법은 하나**(`LEDGER-001@v1`). `paid_at` 제약은 범용 제약(원가계산 실습)이고 대장 행이 아니다.
- **설계서 §3 7단계 행 (c) 정정** — "음수 재고 행 + `CheckConstraint(stock>=0)`" 는 성립하지 않는다. `stock` 은 0단계부터 `PositiveIntegerField`(3단계 실측: 세 경로 모두 `IntegrityError`)라 음수 행을 심을 수 없다. 같은 취지(선언 1줄 + migration + 기존 데이터 정리)를 **`paid_at` 제약**으로 옮긴다. 원문은 지우지 않고 정정 블록.
- **`REFUND-001@v2` 는 하지 않는다.** `paid_at` 을 규칙이 읽게 바꾸면 4·5·6단계 테스트가 `REFUND-001@v1` 문자열을 단언하고 있어 세 단계 채점표를 고쳐야 한다. 대장 갱신(deprecated + 후속 버전)은 8단계 부채 리포트와 함께 별도 실습으로.
- **DENY·REPLAYED·ALREADY 는 도메인 장부에 없다.** "세계가 바뀐 사실" 만 적는다. 호출의 기록은 도구면 궤적의 몫이며, API·콘솔 문의 호출 궤적은 8단계.
- **DELETE 트리거는 걸지 않는다**(테스트 flush). 모델 층 거부 + 정직한 "우회 가능 경로".
- **문맥은 패키지가 묶는다**(v0.2 `context`·미들웨어). 학생 코드는 `current_call()` 만 읽는다. `actor` 는 문맥이 아니라 명시 인자다(토큰 인증 시점 때문).
- **장부에 원문을 넣지 않는다.** `Event.reason` 은 세계의 판정 문장이다.
- 취소 주문의 `paid_at` 은 backfill 하지 않는다 — 모름을 모름으로.

## 9. 빌더 판단·독립 검증 후 정정 (2026-09-07)

빌더(`60b4e19`·`bf1acea`·`131aafb`) 판단 15개는 전부 동의. 독립 검증(별도 Claude 세션, 사양만 열람) 20항목 전원 PASS. 둘이 드러낸 **사양 자체의 문제**를 여기서 바로잡는다. 원문(§2·§4·§6)은 지우지 않는다.

- **§4-2 `intake_order` 의 결함 위치** — "`atomic` 밖 **머리**에서" 는 불가능하다. 주문이 아직 없어 `GenericForeignKey` 의 주어를 만들 수 없다. 정정: 시작 상태는 "`atomic` 블록으로 생성 → **블록 밖에서** 기록". 사실과 기록이 다른 트랜잭션이라는 결함은 그대로 성립한다. 같은 이유로 시작 상태의 `refund.proposed` 는 주어가 `Order` 다(완료 상태는 `Refund`).
- **§2-4 시드** — 3 마이그레이션만으로는 빈 DB(테스트)에서 세계가 서지 않는다. `seed_world` 가 backfill 과 **같은 규칙**(`paid/shipping/completed` → `paid_at = 주문일`)으로 `paid_at` 을 심는다. 채점표 5 는 두 경로에서 같은 답을 준다. 원가계산 실습(contract 먼저 → 깨짐)은 dev DB 와 지시서 절차에서 그대로 성립한다(검증 항목 6 실측).
- **§2-1 `Event.at`** — "전이 메서드가 정한 시각과 같아야 한다" 는 `record` 시그니처에 `at` 이 없어 계약이 아니다. 정정: **`at` 은 기록 시각**(`default=timezone.now`)이고, 사실의 시각은 `after` 에 있다(`order.paid` 의 `after['paid_at']` 이 상태 UPDATE 와 같은 문장의 값). 모델 주석(`ledger/models.py`)도 이 문장으로 고친다(수정 라운드).
- **§2-1 `door` choices ↔ §2-3 기본 `via='web'`** — 두 절이 같은 값 공간을 다르게 정의했다. 정정: `Event.Door` 에 **`web`** 을 더한다("문 표에 없는 경로" 의 정직한 이름). `ITDA['VIA']` 에 없는 경로에서 전이가 일어나면 `web` 으로 남는다. 8단계에서 문이 늘 때 표를 갱신하는 것이 규율(수정 라운드).
- **§4 채점표 9번 이름** — `test_거부·재전송·기존_건은_새_행이_아니다` 의 `·` 는 식별자에 못 쓴다. 구현대로 `test_거부_재전송_기존_건은_새_행이_아니다` 로 읽는다.
- **§6-0 루트 게이트** — "43 + 신규" 는 `fastmcp` extra 가 설치된 venv 전제다(`tests/test_mcp_stdio.py` 6건). 새 worktree 에서는 `uv sync --all-extras` 뒤 실행. 검증 프롬프트에도 이 전제를 적는다.
- **§2-2 `stock.deducted` 의 before/after** — `select_related` 시점의 메모리 값에서 계산한 **스냅샷**이다(재조회하면 다른 트랜잭션이 섞인다 — 빌더 판단 6). SQLite 는 상태 UPDATE 가 먼저 쓰기 잠금을 잡아 갈리지 않지만, READ COMMITTED 백엔드에서는 갈릴 수 있다 — 8단계 배포 소재로 "보장하지 않는 것" 에 한 줄(수정 라운드).
- **부르는 자리** — §2-2 "셋" 은 넷이다(결제 페이지·`race pay`·`tests/stage_04_*` 4곳·`services.pay_order`). 6단계·live 테스트는 수정이 필요 없었다.
- **검증 밖 발견(7단계 무관, 8단계 입력)** — `POST /api/refunds/` 의 `order_id` 에 숫자가 아닌 값을 주면 `filter(pk=…)` 가 터져 500. `InsufficientStock` 500 과 같은 계열 — 8단계 "번역되지 않은 예외" 목록에 넣는다.

## 10. sol 적대 리뷰 후 정정 (2026-09-07)

리뷰 원문·반영 결정: `docs/reviews/2026-09-07-stage-07-sol-리뷰.md`. 총평 불승인 → 발견 8 전부 반영(6 은 이월·문서). 사양이 틀린 곳:

- **§9 "SQLite 는 갈리지 않는다" 는 오류다.** `stock.deducted` 의 before/after 를 `select_related` 스냅샷에서 계산하면 **같은 상품이 두 품목**일 때 경쟁 트랜잭션 없이도 틀린다(실측 20→18 인데 장부는 20→19 두 번). 정정: 조건부 UPDATE 뒤 같은 트랜잭션에서 재고를 **재조회**해 `after`, `before = after + 수량`. UPDATE 가 행 잠금을 쥔 채라 SQLite·PostgreSQL 모두 정확하다. §2-2 표의 "스냅샷" 도 이 문장으로 읽는다.
- **§2-1 `actor` `SET_NULL`** 은 UPDATE 금지 트리거와 동시에 성립하지 않는다(계정 삭제가 `IntegrityError`). 정정: `on_delete=PROTECT` — 장부에 남은 계정은 지울 수 없다. 익명화·삭제 정책은 8단계. "`SET_NULL` 뒤에도 이름은 남는다" 는 "이름이 바뀌어도 당시 이름은 남는다" 로.
- **§2-2 `order.cancelled` 의 before** — 캐시된 `self.order.status` 가 아니라 `atomic` 안에서 DB 를 다시 읽은 값이다.
- **§2-4 backfill 역방향** — `RunPython.noop`. 데이터 마이그레이션은 되돌리며 지우지 않는다. "contract 부터 써 본다" 는 **expand 뒤 backfill 만 생략**한다는 뜻이다. 취소 주문의 `paid_at` 은 "영영 모름" 이 아니라 **현재 DB 만으로 일괄 복원하지 않는다**(DB 밖 근거는 있을 수 있다).
- **§4 채점표** — 값을 안 보는 구멍(재고 값·링크 door·기존 행 backfill)을 보강하고, 1·2·16 은 시그니처 적응 헬퍼로 불러 시작 상태의 실패 사유가 장부의 거짓말이 되게 한다. 4 는 actor 부재를 재는 테스트라 TypeError 실패를 유지. **완료 상태 채점표가 시작 상태 채점표의 상위 집합**이 된다 — 태그 `stage-07-start` 의 채점표는 원판(사후 변경 기록).
- **§2-1 append-only 우회 범위** — `DELETE` 만이 아니다: `INSERT OR REPLACE`(같은 PK 내용 교체)·직접 `INSERT`(가짜 사실)·`DROP TRIGGER`·전이 밖 직접 UPDATE(기록 누락). 전부 `RULES.md` 우회 가능 경로 열에.
- **§5-7 보장하지 않는 것** 에 행 추가: 발급 링크 ↔ 결제 식별자 없음(8단계).

리뷰가 확인해 준 보장(변경 없음): `_resolve_collision` 경로의 이벤트 롤백 · `Order.save()` 실패 시 롤백 · 시작 상태의 의도적 실패 화면 재현 · `sync_to_async(thread_sensitive=True)` 에서 문맥 유지(새 스레드·bind 밖 `on_commit` 은 shell — 자동 전파 보장 없음, 문서화) · `Toolset.call` 의 bind 범위 · fastmcp 임포트 격리.
