# 3단계 — 워밍업

2단계에서 이런 표를 만들었다.

| 목격한 것 | 실제 시행 주체 |
|---|---|
| 403으로 끊겼다 | `contrib.auth` 권한 검사 |
| "나는 점주다"가 안 통했다 | 서명 세션 + `SECRET_KEY` |

전부 **요청이 들어오는 길목**에서 막는 법이었다. 그럼 길목을 안 지나면 어떻게 되나.
shell을 열면 뷰도 없고, 데코레이터도 없고, admin 화면도 없다. 거기서는 무엇이든 되는가.

이번엔 손을 직접 쓴다. **첫 손코딩** — 다만 고칠 코드는 여전히 0줄이고,
치는 것은 shell 명령 세 줄이다. 볼 것은 하나다.

> **법은 어느 층에 사는가.**

## 준비

```bash
just reset-db
uv run python manage.py shell
```

상품 하나를 잡고 pk와 재고를 확인해 둔다.

```python
from shop.models import Product
p = Product.objects.get(name='수제 초코쿠키 6개입')
p.pk, p.stock          # 예: (1, 40)
```

이 상품의 재고를 **음수로 만드는 것**이 이번 실습의 목표다. 세 가지 경로로 시도한다.
갈수록 Django에서 멀어지는 순서다.

## 명령 — 세 경로로 같은 벽을 두드린다

### 경로 1 — ORM 정규 경로

가장 평범한 방법. 필드에 대입하고 저장한다.

```python
p.stock = -5
p.save()
```

```
django.db.utils.IntegrityError: CHECK constraint failed: stock
```

에러 메시지를 그대로 복사해 둔다(제출물 1).

> 왜 `ValidationError`가 아닌가? `save()`는 `full_clean()`을 부르지 않는다.
> 즉 **Python 검증은 통과했다.** 막은 것은 그 뒤다.

### 경로 2 — ORM 우회 경로

`save()`도 `clean()`도 모델 메서드도 전부 건너뛰는 방법이 있다.
`QuerySet.update()`는 Python 객체를 거치지 않고 UPDATE 문 하나를 바로 쏜다.
`mark_paid()`가 재고를 깎을 때 쓰는 것과 같은 형태다.

```python
from django.db.models import F
Product.objects.filter(pk=p.pk).update(stock=F('stock') - 999)
```

```
django.db.utils.IntegrityError: CHECK constraint failed: stock
```

`save()`에 넣어 둔 검증이 있었더라도 이 경로에는 소용없었을 것이다.
그런데도 막혔다. **막은 것은 Python이 아니다.**

### 경로 3 — Django 완전 우회

shell을 나온다. 이번엔 Django를 아예 쓰지 않는다.

```bash
sqlite3 db.sqlite3 "UPDATE shop_product SET stock = -1 WHERE id = 1;"
```

```
Error: stepping, CHECK constraint failed: stock (19)
```

(sqlite3 버전에 따라 `Runtime error: CHECK constraint failed: stock (19)`로 나오기도 한다.
어느 쪽이든 끝의 `(19)`가 SQLite의 `SQLITE_CONSTRAINT` 코드다.)

Django가 실행되고 있지도 않은데 거부당했다. 그럼 그 법의 원문은 어디에 있나.

```bash
sqlite3 db.sqlite3 ".schema shop_product"
```

```sql
CREATE TABLE IF NOT EXISTS "shop_product" (
    "id" integer NOT NULL PRIMARY KEY AUTOINCREMENT,
    ...
    "price" integer unsigned NOT NULL CHECK ("price" >= 0),
    "stock" integer unsigned NOT NULL CHECK ("stock" >= 0),
    ...
);
```

테이블 정의 안에 들어 있다. 그리고 이 한 줄의 출처는 `shop/models.py`의

```python
stock = models.PositiveIntegerField('재고')
```

**단어 하나**다. `Positive`라고 쓴 순간 `CHECK ("stock" >= 0)`가 마이그레이션을 타고
DB에 새겨졌다. 0단계에서 이미 심어져 있었고, 아무도 그 이야기를 해 주지 않았다.

## 이 단계의 한 문장

| 법이 사는 층 | 지켜지는 범위 | 뚫는 방법 |
|---|---|---|
| 프롬프트("재고를 음수로 만들지 마") | AI가 협조할 때만 | 무시하면 끝 |
| 화면(입력 폼 `min=0`) | 그 폼을 쓸 때만 | 다른 화면·API |
| 뷰(`if stock < 0: return 400`) | 그 뷰를 지날 때만 | 다른 뷰·shell·배치 |
| 모델(`save()`의 검증) | Python 객체를 거칠 때만 | `update()`·raw SQL |
| **DB 제약** | **전부** | 없음 |

> **법이 내 코드가 아니라 DB에 산다.**
> 뷰로 오든, shell로 오든, 다른 언어로 오든, 다른 프로세스로 오든 — 지켜진다.
> `PositiveIntegerField` 한 단어가 그 선언이었다.

여기서 방금 본 `IntegrityError`는 **실패가 아니라 보장**이다.
세계가 자기 약속을 지키느라 낸 소리다. 앞으로 이 소리를 여러 번 다시 듣게 된다.

## 이어지는 질문

재고에는 이런 것이 있다. **그럼 주문에는?**

2단계 마지막에 만든 도메인 법 목록을 다시 본다.

- 환불은 7일 안에만 된다
- 5만원을 넘으면 점주에게 올린다
- 주문은 `pending`에서만 `paid`로 갈 수 있다

세 번째 문장을 골라 방금과 똑같이 시험해 보라.
**이미 결제 완료된 주문을 한 번 더 결제 완료로 만들면 어떻게 되는가?**

```python
from orders.models import Order
o = Order.objects.get(order_number='SEED-0002')
o.status                       # 'paid' — 이미 결제 완료
# 여기서부터는 스스로. mark_paid() 를 한 번 더 불러 보라.
# 재고가 어떻게 되는지, 예외가 나는지, 아무 일도 없는지를 눈으로 확인한다.
```

`.schema orders_order`도 열어 본다. `status` 옆에 `CHECK`가 있는가?

무엇을 봤는지 한 줄로 적어 두고 이 단계를 닫는다. **여기서는 고치지 않는다.**
그 답을 들고 4단계로 간다.

## 의도적 실패

이 단계의 `IntegrityError` 세 번은 실패가 아니라 **목격 대상**이다.
에러가 안 나면 그때가 진짜 실패다 — `just reset-db`부터 다시 한다.

## 수정

없다. 코드를 한 줄도 고치지 않는다.

## 검증

```bash
just test 03
```

경로 1·2·3을 각각 `IntegrityError`로 단언한다. 2단계와 마찬가지로 코드를 고치지 않는
단계라 태그는 `stage-03-done` 하나다.

> 테스트에서는 세 시도를 각각 `transaction.atomic()` 블록 안에서 일으킨다.
> 제약 위반은 트랜잭션을 깨뜨리므로, 감싸지 않으면 뒤따르는 쿼리가 전부
> `TransactionManagementError`로 죽는다. shell에서 이어서 실습할 때도 같다 —
> `IntegrityError`가 난 뒤 뭔가 이상하면 shell을 껐다 켜라.
