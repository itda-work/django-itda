# 7단계 — 기록

지금까지 세계는 **움직이기만** 했다. 누가 언제 어느 문으로 무엇을 근거로
움직였는지는 `Refund.decided_via` 한 칸과 `LogEntry` **0건**이 전부다.

이번 법은 하나다 — **세계가 움직인 사실은 세계와 같은 트랜잭션에서 장부에
남는다. 그리고 장부는 고쳐 쓸 수 없다.**

관통 문장에 마지막 한 겹이 붙는다: *제안은 AI, 판정은 세계, 확정은 사람 —
그리고 그 둘의 기록은 세계 자신이 남긴다.*

## 준비

```bash
just reset-db
cat agent/prompts/ai_staff.md
```

문장이 하나 늘었다. **이사 표시가 없다** — 아무도 안 지켜 준다는 뜻이다.

> 7. **세계를 움직인 일은 빠짐없이 장부에 남겨라 — 누가·언제·어느 문으로·어떤
>    규칙으로. 장부는 고치지 마라.**

앞 단계들이 「이 단계가 보장하지 않는 것」 표에 적어 둔 "7단계" 행을 모아 읽는다.

| 어디 | 남겨 둔 말 |
|---|---|
| 2단계 | admin 커스텀 액션(승인)은 `LogEntry` **0건** — 폼 변경만 남는다(실측 2026-09-05) |
| 4단계 | 전이에 `actor` 가 없다. 결제 시각(`paid_at`)이 없어 환불 기한은 `created_at` 가정 위에 선다 |
| 5단계 | 경합의 **패자**는 아무 데도 안 남는다. 재전송도 마찬가지다 |
| 6단계 | 링크 발급·사용은 **아무 데도 안 남는다**(무상태 토큰의 대가). `actor` 인자는 자리만 뚫려 있다 |

## 명령

시작 상태에는 장부(`ledger.Event`)가 **이미 있다.** 표를 보는 도구도 있다.

```bash
just race pay SEED-0004     # 같은 결제 두 개를 동시에 쏜다
just ledger                 # 장부를 본다
```

세계는 하나만 결제된다(4단계 rowcount 계약). 그런데 장부는:

```

[B] 200 ALLOW                SEED-0004 을(를) 결제 완료로 옮겼습니다.
```

**결제 2건, 차감 2건.** 세계는 한 번 움직였는데 장부는 두 번이라고 말한다.
`자리` 칸도 비어 있다 — 누가 결제했는지 장부는 모른다.

콘솔(`/agent/`)의 ⑥ 카드(이미 결제된 주문에 링크 재발급, DENY)를 누른 뒤
`just ledger` 를 다시 본다. **`payment_link.issued` 가 또 한 줄 있다** —
발급되지 않은 링크가 발급됐다고 적혀 있다.

admin 에서 환불을 승인한다. `just ledger` — **아무것도 없다.**
서비스 층을 지나지 않는 문은 이 장부에 닿지 못한다. 발견 3 이 그대로다.

```bash
just test 07     # 18개 중 16개가 실패한다 (start 태그의 채점표 기준)
```

통과하는 둘은 채점이 아니라 **준비 확인**이다.

| 통과하는 테스트 | 왜 시작 상태에서도 통과하나 |
|---|---|
| `test_도구_호출과_장부는_같은_call_id_로_잇닿는다` | 호출 문맥은 패키지가 준다(django-itda v0.2 `contextvars` + 미들웨어). 학생이 고칠 것은 "어디서 적는가"이지 "어떻게 잇는가"가 아니다 |
| `test_장부는_고칠_수_없다_모델_층` | `Event.save`/`delete` 의 거부는 시작 상태에 이미 있다. 못 막는 것은 `QuerySet.update()` 이고, 그건 DB 층의 몫이다 |

## 의도적 실패

셋이다.

### (a) `mark_paid()` 는 누가 결제했는지 받지 않는다

`orders/models.py:Order.mark_paid(self)` — 4단계 표의 "전이에 actor 없음"이
그대로다. 장부에 적을 자리가 없으니 `자리` 칸이 빈다.

### (b) 장부가 사실 **전에**, 트랜잭션 **밖에서** 적힌다

`orders/services.py` 를 연다. 서비스 함수들이 **머리에서** 장부를 적는다 —
판정도 전이도 부르기 전에, 트랜잭션 밖에서.

```python
def pay_order(order):
    Event.record(..., transition='order.paid', after={'status': 'paid'})   # ← 먼저 적는다
    for item in order.items.select_related('product'):
        Event.record(..., transition='stock.deducted', ...)                 # ← 이것도
    try:
        order.mark_paid()                                                   # ← 세계는 그 다음에 움직인다
```

**의도를 사실로 적는 장부는 rowcount 를 무시하는 것과 같다.** 4단계에서
"UPDATE 를 쏘고 rowcount 를 안 봤다"가 버그였던 그 구조가, 장부로 돌아왔다.

### (c) `Order.paid_at` 이 없다

4단계 `Refund.decide` 의 주석 — *"결제일은 `created_at` 으로 본다. 결제 시각을
따로 들고 있지 않아서 두는 교육상 가정"* — 이 아직 가정이다.

## 수정

순서가 있다. 장부를 옮기는 것이 먼저다 — `paid_at` 은 옮긴 장부가 적을 값이다.

### 1. 장부를 옮긴다 — 사실 뒤, 같은 트랜잭션

`orders/services.py` 의 사전 기록을 **전부 지운다.** 그리고 기록을 사실이 나는
자리로 옮긴다.

| 사실 | 적는 자리 | 왜 거기인가 |
|---|---|---|
| `order.placed` | `services.intake_order` 의 `atomic` 안, 생성 뒤 | 접수에는 전이 메서드가 없다. 서비스가 그 자리다 |
| `order.paid` | `Order.mark_paid` 의 `atomic` 안, **rowcount 확인 뒤·재고 차감 뒤** | rowcount 0 이면 세계가 안 움직였다 |
| `stock.deducted` | `mark_paid` 의 품목 루프, **`updated` 확인 뒤** 품목마다 | 깎이지 않은 재고를 깎았다고 적으면 4단계의 그 버그다. 값은 **재조회한다** — 아래 참조 |
| `refund.proposed` | `Refund.apply` 의 `atomic` 안, `create` 뒤 | 판정 뒤라 **각인**(`rule_ids`)이 있다 |
| `refund.approved` + `order.cancelled` | `Refund.approve` 의 `atomic` 안, rowcount 뒤 | 한 요청이 만든 **두 사실** — 같은 `call_id` 로 묶인다 |
| `refund.rejected` | `Refund.reject` 의 `atomic` 안, rowcount 뒤 | |
| `payment_link.issued` | `services.issue_payment_link`, **격상일 때만** | 발급하지 않은 링크는 사실이 아니다 |

**적는 값은 읽어 둔 객체가 아니라 DB 다.** 두 자리에서 같은 함정이 나온다.

- `stock.deducted` — `select_related` 로 읽은 상품 객체의 `stock` 은 루프가
  도는 동안 늙는다. 같은 상품이 두 품목인 주문에서는 두 줄 다 최초 재고를
  말한다(세계는 20→18 인데 장부는 20→19 가 두 번). 조건부 UPDATE **뒤**
  같은 트랜잭션에서 재고를 다시 읽어 `after` 로 쓰고, `before` 는 거기에
  수량을 되더한다. 방금 쏜 UPDATE 가 그 행의 잠금을 쥔 채라 정확하다.
- `order.cancelled` — `Refund.approve` 의 `self.order` 는 제안 시점의 캐시다.
  취소 직전 상태는 `atomic` 안에서 다시 읽는다. 취소 자체는 그 값과 무관하게
  진행한다(승인된 환불은 어느 상태의 주문이든 취소로 보낸다).

**같은 트랜잭션이라는 사실만으로 스냅샷이 정확해지지는 않는다.**

장부에 `actor` 로 남은 계정은 **지울 수 없다**(`on_delete=PROTECT`).
`SET_NULL` 이면 계정 삭제가 장부 행을 UPDATE 하려 들고 append-only 트리거가
그것을 거절한다 — 장부 불변과 계정 삭제는 동시에 성립하지 않아서 계약을
골라야 한다. 여기서는 장부가 이긴다. 익명화·삭제 정책은 8단계다.

`Refund.approve` 를 **모델 안**에 두는 것이 요점이다. 서비스 층에 두면 admin
액션처럼 서비스를 지나지 않는 문이 통째로 빠진다 — 발견 3 이 그 자리였다.

`Order.mark_paid()` 가 **`mark_paid(actor)`** 가 된다. 부르는 자리는 셋이다:
`services.pay_order(actor, order)`(결제 페이지가 `request.user` 를 넘긴다),
`just race pay`(주문자를 넘긴다), 4단계 채점표.

**거부되면 아무것도 적지 않는다.** DENY·REPLAYED·ALREADY 는 세계를 바꾸지
않았으므로 도메인 장부에 행이 없다. 불린 사실은 도구면 궤적(`ToolCall`)의 몫이다.

### 2. `paid_at` — expand → backfill → contract

**expand 뒤 backfill 만 건너뛰어 본다.** 열(`paid_at`)은 추가하고, 기존 행을
채우는 `RunPython` 없이 `CheckConstraint` 를 얹은 뒤 `just reset-db` 없이
`migrate` 한다(아직 없는 열을 참조하는 제약만 먼저 얹는 것은 다른 실패다 —
그건 스키마가 성립하지 않는 경우이고, 여기서 보려는 것은 **데이터**다).

```
django.db.utils.IntegrityError: CHECK constraint failed: order_paid_has_paid_at
```

**이것이 원가계산이다.** 선언은 한 줄인데, 값은 **이미 있는 행**이 치른다.
SEED-0001·0002·0003 은 결제 완료 상태이면서 결제 시각이 없다 — 그런 칸이
없던 시절에 만들어진 행이기 때문이다.

그래서 셋으로 나눈다.

| 순서 | 마이그레이션 | 하는 일 |
|---|---|---|
| expand | `0005_order_paid_at` | `paid_at = DateTimeField(null=True, blank=True)` — 아무것도 깨지 않는다 |
| backfill | `0006_backfill_paid_at` | `RunPython` — `paid`·`shipping`·`completed` 이고 `paid_at IS NULL` 인 행에 `paid_at = created_at` |
| contract | `0007_order_paid_has_paid_at` | `CheckConstraint(condition=Q(status__in=['pending','cancelled']) \| Q(paid_at__isnull=False))` |

**취소 주문은 채우지 않는다.** 결제 뒤 취소인지 결제 전 취소인지 —
**지금 DB 에 남은 것만으로는 일괄 복원할 근거가 없다.** `Refund.decided_at` 은
환불 결정 시각이지 결제 시각이 아니고, 환불 판정은 결제 대기 주문도 허용한다.
모름을 모름으로 둔다. 채워 넣는 순간 장부가 아니라 추측이 데이터가 된다.
(DB 밖의 근거 — 과거 실접속 기록 같은 것 — 으로 개별 주문의 결제를 아는 것은
별개다. 일괄 마이그레이션이 할 일이 아닐 뿐이다.)

`0006` 의 **역방향은 아무것도 하지 않는다**(`RunPython.noop`). 되돌리며
지우는 backfill 은 자기가 채운 행과 그 뒤 실제로 결제된 행을 구별하지 못해
관측된 결제 시각까지 NULL 로 만든다. 데이터 마이그레이션은 앞으로만 간다.

`mark_paid` 는 `paid_at` 을 **상태 UPDATE 와 같은 문장**에서 채운다.

```python
Order.objects.filter(pk=self.pk, status=PENDING).update(status=PAID, paid_at=paid_at)
```

두 문장으로 나눌 수 **없다** — 제약이 살아 있는 한 "결제됐는데 결제 시각이
없는" 첫 번째 UPDATE 를 DB 가 그 자리에서 거절하기 때문이다. 제약이 무력해지는
것이 아니라, **제약이 같은 문장을 강제한다.**

### 3. DB 층 append-only

모델 층은 `QuerySet.update()` 를 못 막는다 — `save()` 를 지나지 않기 때문이다.
`ledger/migrations/0002_append_only_trigger.py` 가 그것을 막는다.

```sql
CREATE TRIGGER ledger_event_no_update BEFORE UPDATE ON ledger_event
BEGIN SELECT RAISE(ABORT, 'LEDGER-001@v1: 장부는 고치지 않는다'); END;
```

`RAISE(ABORT)` 는 `SQLITE_CONSTRAINT` 라 Django 에서 `IntegrityError` 로 올라온다.
우리 예외(`LedgerImmutable`)가 아닌 것이 의도다 — 막은 것이 우리 코드가 아니다.

**DELETE 트리거는 걸지 않는다.** Django 의 테스트 DB flush 가 `DELETE FROM` 을
쓰기 때문이다. 삭제는 모델 층만 막고, 그 한정을 `RULES.md` 에 정직하게 적는다.

### 4. 대장과 프롬프트

`orders/rules.py` 에 `LEDGER_001`·`RULE_TEXTS` 한 줄, `RULES.md` 에 한 행,
프롬프트 7번에 이사 표시. 원문은 지우지 않는다.

### Django 가 준 자리

| 오늘 쓴 것 | 무엇을 해 주나 |
|---|---|
| `transaction.atomic` | 사실과 기록이 **같이** 커밋되거나 **같이** 되돌아간다 |
| `contextvars`(django-itda v0.2) | 문맥은 문이 묶는다 — 전이 메서드가 요청을 몰라도 "어느 문으로" 가 남는다 |
| `GenericForeignKey`·`ContentType` | 주어가 무엇이든 되는 한 표 — 주문·상품·환불이 같은 장부에 앉는다 |
| `RunPython` / `RunSQL` | 기존 데이터 정리 · DB 트리거 |
| `CheckConstraint` | 경로를 지나지 않아도 걸리는 선언 |
| `Model.save`/`QuerySet` 재정의 | 모델 층의 거부 — 화면 한 겹이 아니라 코드 한 겹 |

(`refund.approved`·`order.cancelled`)이 **같은 `call_id`** 로 나란히 있다.
`just ledger --call <앞 8자>` 로 한 호출의 사슬만 뽑을 수 있다.

Django 밖에서도 막히는지 본다.

```bash
sqlite3 db.sqlite3 "UPDATE ledger_event SET reason='조작' WHERE id=1;"
# Error: stepping, LEDGER-001@v1: 장부는 고치지 않는다 (19)
```

## 이 단계의 한 문장

> **장부는 의도를 적지 않는다. 사실을, 사실이 난 그 트랜잭션에서 적는다.**

## 이 단계가 보장하지 않는 것

| 못 하는 것 | 왜 | 언제 |
|---|---|---|
| 거부·패자의 장부(API·콘솔 문) | 세계가 안 바뀌었으니 도메인 장부엔 없고, `ToolCall` 은 MCP 문만 잡는다 | 8단계 — 도구면 생성이 API 도 `Toolset` 을 지나게 하면 잡힌다 |
| SQL 직접 조작 | 갱신 금지 트리거는 UPDATE 만 본다 — SQLite·PostgreSQL 둘 다다(PG 는 `ERRCODE '23000'` 트리거 함수, Django `IntegrityError` 로 올라옴을 실측 2026-09-19). `DELETE FROM`(테스트 flush 때문에 안 막았다 — PG 에서도 트리거 없이 지워짐을 실측) · `INSERT OR REPLACE`(같은 PK 의 내용 교체, SQLite 문법) · 직접 `INSERT`(가짜 사실 추가) · `DROP TRIGGER`(권한이 있으면 법 자체를 걷어낸다) · 전이 밖 직접 UPDATE(기록이 아예 안 남는다) | 8단계 — DB 역할 권한(PostgreSQL `REVOKE DELETE`·`REVOKE TRIGGER`, 또는 `BEFORE DELETE` 트리거 — 운영 소재) |
| 어떤 링크로 결제했는가 | 발급 이벤트와 결제 이벤트를 잇는 식별자가 없다. 같은 주문에 링크를 둘 발급하고 하나로 결제하면 장부만으로는 어느 것인지 모른다(발급과 결제는 다른 요청이라 `call_id` 도 다르다). 토큰 타임스탬프는 같은 초에 발급되면 겹쳐서 식별자가 못 된다 | 8단계 |
| 장부에 남은 계정의 삭제 | 지울 수 없다(`PROTECT`). 장부 불변을 고른 대가다 | 8단계 — 익명화·삭제 정책 |
| 결제일 가정 | `REFUND-001@v1` 은 여전히 `created_at` 기준이다. `paid_at` 이 있어도 규칙이 아직 안 읽는다 | `REFUND-001@v2` — 대장 갱신 실습으로 뒤로 |
| 취소 주문의 `paid_at` | 장부 이전의 취소는 **현재 DB 만으로는** 결제 여부를 가릴 근거가 없다. 일괄로 채우지 않는다 | DB 밖의 근거로 개별 복원하는 것은 별개 |
| `LogEntry` | 그대로 **0건**이다. Django 의 장부를 고치지 않고 우리 장부를 만들었다 | 합치지 않는다 |
| 장부 오염 | `reason` 에 세계의 문장만 넣는다. 고객·모델의 원문은 `Refund.reason` 에만 있다 | 장부에서 원문을 보고 싶은 유혹이 곧 오염 벡터다 |
| 상관 ID 의 출처 | `X-Request-ID` 를 **믿는다**(형식만 검사). 클라이언트가 남의 ID 를 붙일 수 있다 | 8단계 |
| 시계 | `at` 은 서버 시계다. 단조 증가 보장 없음 | — |
