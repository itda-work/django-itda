# 7단계 — 기록

> **시작 상태(`stage-07-start`)의 뼈대다.** 「수정」 이하는 완료 상태에서 채운다.

지금까지 세계는 **움직이기만** 했다. 누가 언제 어느 문으로 무엇을 근거로
움직였는지는 `Refund.decided_via` 한 칸과 `LogEntry` **0건**이 전부다.

이번 법은 하나다 — **세계가 움직인 사실은 세계와 같은 트랜잭션에서 장부에
남는다. 그리고 장부는 고쳐 쓸 수 없다.**

관통 문장에 마지막 한 겹이 붙는다: *제안은 AI, 판정은 세계, 확정은 사람 —
그리고 그 둘의 기록은 세계 자신이 남긴다.*

## 준비

```bash
just reset-db
cat agent/prompts/ai_staff.md
```

문장이 하나 늘었다. **이사 표시가 없다** — 아무도 안 지켜 준다는 뜻이다.

> 7. **세계를 움직인 일은 빠짐없이 장부에 남겨라 — 누가·언제·어느 문으로·어떤
>    규칙으로. 장부는 고치지 마라.**

앞 단계들이 「이 단계가 보장하지 않는 것」 표에 적어 둔 "7단계" 행을 모아 읽는다.

| 어디 | 남겨 둔 말 |
|---|---|
| 2단계 | admin 커스텀 액션(승인)은 `LogEntry` **0건** — 폼 변경만 남는다(실측 2026-09-05) |
| 4단계 | 전이에 `actor` 가 없다. 결제 시각(`paid_at`)이 없어 환불 기한은 `created_at` 가정 위에 선다 |
| 5단계 | 경합의 **패자**는 아무 데도 안 남는다. 재전송도 마찬가지다 |
| 6단계 | 링크 발급·사용은 **아무 데도 안 남는다**(무상태 토큰의 대가). `actor` 인자는 자리만 뚫려 있다 |

## 명령

시작 상태에는 장부(`ledger.Event`)가 **이미 있다.** 표를 보는 도구도 있다.

```bash
just race pay SEED-0004     # 같은 결제 두 개를 동시에 쏜다
just ledger                 # 장부를 본다
```

세계는 하나만 결제된다(4단계 rowcount 계약). 그런데 장부는:

```
[A] 409 DENY [ORDER-001@v1]  결제 대기 상태가 아니다(조건 불일치).
[B] 200 ALLOW                SEED-0004 을(를) 결제 완료로 옮겼습니다.

시각            문     자리  전이            대상                           판정   규칙  호출
──────────────  ─────  ────  ──────────────  ─────────────────────────────  ─────  ────  ────
09-07 05:48:30  shell  —     order.paid      SEED-0004 (bob)                ALLOW  —     —
09-07 05:48:30  shell  —     order.paid      SEED-0004 (bob)                ALLOW  —     —
09-07 05:48:30  shell  —     stock.deducted  [간식] 한정판 흑임자 다쿠아즈  ALLOW  —     —
09-07 05:48:30  shell  —     stock.deducted  [간식] 한정판 흑임자 다쿠아즈  ALLOW  —     —
```

**결제 2건, 차감 2건.** 세계는 한 번 움직였는데 장부는 두 번이라고 말한다.
`자리` 칸도 비어 있다 — 누가 결제했는지 장부는 모른다.

콘솔(`/agent/`)의 ⑥ 카드(이미 결제된 주문에 링크 재발급, DENY)를 누른 뒤
`just ledger` 를 다시 본다. **`payment_link.issued` 가 또 한 줄 있다** —
발급되지 않은 링크가 발급됐다고 적혀 있다.

admin 에서 환불을 승인한다. `just ledger` — **아무것도 없다.**
서비스 층을 지나지 않는 문은 이 장부에 닿지 못한다. 발견 3 이 그대로다.

```bash
just test 07     # 18개 중 16개가 실패한다
```

통과하는 둘은 채점이 아니라 **준비 확인**이다.

| 통과하는 테스트 | 왜 시작 상태에서도 통과하나 |
|---|---|
| `test_도구_호출과_장부는_같은_call_id_로_잇닿는다` | 호출 문맥은 패키지가 준다(django-itda v0.2 `contextvars` + 미들웨어). 학생이 고칠 것은 "어디서 적는가"이지 "어떻게 잇는가"가 아니다 |
| `test_장부는_고칠_수_없다_모델_층` | `Event.save`/`delete` 의 거부는 시작 상태에 이미 있다. 못 막는 것은 `QuerySet.update()` 이고, 그건 DB 층의 몫이다 |

## 의도적 실패

셋이다.

### (a) `mark_paid()` 는 누가 결제했는지 받지 않는다

`orders/models.py:Order.mark_paid(self)` — 4단계 표의 "전이에 actor 없음"이
그대로다. 장부에 적을 자리가 없으니 `자리` 칸이 빈다.

### (b) 장부가 사실 **전에**, 트랜잭션 **밖에서** 적힌다

`orders/services.py` 를 연다. 서비스 함수들이 **머리에서** 장부를 적는다 —
판정도 전이도 부르기 전에, 트랜잭션 밖에서.

```python
def pay_order(order):
    Event.record(..., transition='order.paid', after={'status': 'paid'})   # ← 먼저 적는다
    for item in order.items.select_related('product'):
        Event.record(..., transition='stock.deducted', ...)                 # ← 이것도
    try:
        order.mark_paid()                                                   # ← 세계는 그 다음에 움직인다
```

**의도를 사실로 적는 장부는 rowcount 를 무시하는 것과 같다.** 4단계에서
"UPDATE 를 쏘고 rowcount 를 안 봤다"가 버그였던 그 구조가, 장부로 돌아왔다.

### (c) `Order.paid_at` 이 없다

4단계 `Refund.decide` 의 주석 — *"결제일은 `created_at` 으로 본다. 결제 시각을
따로 들고 있지 않아서 두는 교육상 가정"* — 이 아직 가정이다.
