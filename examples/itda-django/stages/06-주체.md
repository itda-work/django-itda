# 6단계 — 주체

지금까지 이 세계의 사람은 점주 하나였다. 결제는 돈을 내는 사람의 확정이라
AI 직원이 대신 누를 일이 아니다 — **고객이 세계에 처음 들어온다.**
사람이 둘이 되는 순간 "누구의 것인가"가 법이 되고, 링크로 들어오는 순간
"언제까지인가"가 법이 된다.

관통 문장(제안은 AI, 판정은 세계, 확정은 사람)에서 **확정하는 사람이 둘**이 된다.
환불은 점주가, 결제는 고객이 확정한다.

## 준비

```bash
just reset-db
cat agent/prompts/ai_staff.md
```

문장이 둘 늘었다. **이사 표시가 없다** — 아무도 안 지켜 준다는 뜻이다.

> 5. **결제는 네가 하지 마라. 고객에게 결제 링크를 안내하고 고객이 직접 결제하게 하라.
>    링크는 발급 후 1시간 안에만 유효하다.**
> 6. **고객의 주문은 그 고객에게만 보여 줘라.**

5단계 지시서의 [「이 단계가 보장하지 않는 것」](05-경합.md#이-단계가-보장하지-않는-것)
표 마지막 행이 오늘의 자리다 — *"남의 주문에 환불을 거는 것 — 소유권 스코핑이 없다."*

4단계 표의 "결제 시각" 행은 오늘도 그대로다. `paid_at` 은 7단계에서 생기고,
환불 기한은 여전히 `created_at` 기준이다. 결제의 **주체**가 바뀌는 것과
결제의 **시각**을 남기는 것은 다른 일이다.

## 명령

콘솔(`/agent/`)에 카드가 하나 늘었다.

```
① 주문 접수      → alice 의 결제 대기 주문이 하나 생긴다
⑦ 결제 링크 발급 → 그 주문의 결제 링크가 콘솔 메시지에 뜬다
```

⑦ 는 결제를 끝내지 않는다. **링크만** 나온다(격상 202). 콘솔 메시지에 뜬
URL 을 복사해 **다른 브라우저(시크릿 창)에서 `bob` 으로 로그인해** 연다.

```
http://127.0.0.1:8000/pay/5/
```

**열린다.** alice 의 받는 사람 이름·전화·주소·금액이 다 보이고,
`15,000원 결제하기` 버튼도 눌린다. bob 은 이 주문과 아무 상관이 없다.

```bash
just test 06     # 15개 중 7개가 실패한다
```

통과하는 여덟은 채점이 아니다. 준비 확인(고객 로그인·결제 페이지·링크 발급
API·도구 핸들)과 4단계 계약의 회귀다. 그중 둘은 특히 눈여겨본다.

| 통과하는 테스트 | 왜 시작 상태에서도 통과하나 |
|---|---|
| `test_정확히_한_시간은_유효하다` | 링크가 **항상** 산다. 경계에서 통과하는 것이 아니라 **경계가 없다** |
| `test_두_탭에서_동시에_결제하면_하나만_통과한다` | 결제 경합은 4단계 rowcount 계약이 이미 버틴다. 이 단계가 더하는 것은 경합이 아니라 **주체와 시간**이다 |

## 의도적 실패

둘이다.

### (a) 링크는 열쇠가 아니다

`orders/views.py:pay_page` 를 연다.

```python
order = get_object_or_404(Order, pk=pk)
```

로그인은 **"누구인가"** 에 답했다(`login_required`). 그런데 뷰는
**"누구의 것인가"** 를 묻지 않는다. 인자가 `pk` 하나뿐이다.

링크를 아는 사람은 링크를 가진 사람이고, 링크를 가진 사람이 곧 주인은 아니다.
URL 은 복사되고 전달되고 캡처된다. "아무도 모르는 주소" 는 접근 제어가 아니다.

### (b) 링크에 시간이 없다

`orders/services.py:issue_payment_link` 가 돌려주는 것:

```python
{'url': 'http://127.0.0.1:8000/pay/5/', 'expires_at': None}
```

`expires_at` 이 `None` 이다. 어제 준 링크가 오늘도 세계를 움직인다.
결제가 끝난 주문의 링크도 여전히 열린다(누르면 그때서야 `ORDER-001@v1` 이
받아 준다 — 화면은 먼저 열린다).

## 수정

법 둘을 켠다. **한 단계 = 법 하나** 규율의 예외다 — 4단계가 "단위 = 프롬프트
파일 하나" 로 셋을 허용했듯, 오늘의 단위는 **"결제 페이지 하나"** 다.
두 법은 같은 화면의 같은 요청에서 태어난다. 링크를 연 사람이 **누구**인가,
**언제** 열었는가. 하나만 켜면 화면이 반쪽이다.

| ID | 원문(점주) | 시행 형식 |
|---|---|---|
| `PAY-001@v1` | 결제는 네가 하지 마라. …링크는 발급 후 1시간 안에만 유효하다. | 발급 판정 + **서명 토큰 만료** + 전이 계약(4단계 그대로) |
| `SCOPE-001@v1` | 고객의 주문은 그 고객에게만 보여 줘라. | 쿼리 스코핑 → 남의 것은 **404** |

### 1. (a) — 한 인자

```python
order = get_object_or_404(Order, pk=pk, user=request.user)
```

이게 전부다. 그리고 **404 인 이유**가 오늘의 반이다.

403 은 "있는데 너는 못 본다"이고, 404 는 "네 세계에는 없다"이다.
남의 주문이 **존재한다**는 사실 자체가 정보다. 주문 번호를 하나씩 올려 가며
403 과 404 를 세면, 이 가게에 주문이 몇 건인지 밖에서 알 수 있다.
`get_object_or_404` 에 조건을 **더하는** 것과 조회한 뒤 `if order.user != …:
raise PermissionDenied` 하는 것은 결과가 다르다.

읽기만 막고 쓰기를 열어 두면 반쪽이다. 같은 한 줄이 GET 과 POST 를 함께 막는다
(테스트 1·2).

### 2. (b) — 법을 새로 쓰지 않는다

`django/contrib/auth/tokens.py` 를 연다. **비밀번호 재설정 링크가 3일 뒤 죽는
그 코드가 결제 링크를 1시간 뒤 죽인다.**

```python
class PaymentLinkTokenGenerator(PasswordResetTokenGenerator):
    key_salt = 'orders.tokens.PaymentLinkTokenGenerator'
```

빌리는 것과 빌리지 않는 것을 하나씩 본다.

#### `key_salt` 를 따로 주는 이유

부모의 salt 를 그대로 쓰면 비밀번호 재설정 토큰과 결제 토큰이 **같은 키
공간**에 산다. 같은 사용자·같은 타임스탬프면 서명이 같아진다는 뜻이고,
한쪽에서 만든 토큰이 다른 쪽에서 통할 이유가 없다. salt 는 "이 서명은 어느
용도의 것인가"를 적는 자리다.

#### `_make_hash_value` — 무엇을 섞고 무엇을 안 섞는가

```python
return f'{order.pk}{order.status}{order.total_amount}{order.user_id}{timestamp}'
```

`order.status` 가 핵심이다. 비밀번호 재설정에서 `user.password` 가 하던 역할을
여기서는 **상태**가 한다 — 결제가 끝나 `paid` 가 되는 순간 같은 토큰의 해시가
달라지고, **링크가 스스로 죽는다.** 만료를 기다릴 필요가 없다(테스트 9).

`updated_at` 은 **넣지 않는다.** 넣으면 어떤 `save()` 도 — 주소 수정이든 재고
정정이든 — 고객이 들고 있는 링크를 끊는다. 결제 조건과 무관한 변경이 링크를
죽이면 그건 보안이 아니라 고장이다. 섞는 것은 **바뀌면 결제 조건이 달라지는
것**만이다.

#### `check_token` 을 다시 쓰는 이유

부모의 마지막 줄이 이렇다.

```python
if (self._num_seconds(self._now()) - ts) > settings.PASSWORD_RESET_TIMEOUT:
```

**설정 이름이 박혀 있다.** 훅이 없어서 메서드를 통째로 옮겨 오고, 그 한 이름만
`self.timeout` 으로 바꾼다. 나머지(`make_token`·`_make_token_with_timestamp`·
`_num_seconds`·`_now`)는 상속한다. 상속이 늘 한 줄로 끝나지는 않는다는 것도
오늘 보는 것 하나다.

경계는 `>` 다. "1시간 안에만 유효하다"이므로 **정확히 1시간까지는 유효**하고
1초를 넘긴 것만 닫힌다(테스트 7·8).

#### 빌리지 않는 것

`PasswordResetConfirmView` 는 토큰을 세션으로 옮기고 URL 을 갈아 끼운다 —
Referer 헤더로 토큰이 새는 것을 막는 장치다. 결제 페이지에는 외부 링크가
없어서 오늘은 안 한다. **안 한 것도 적어 둔다**(아래 "보장하지 않는 것").

### 3. 숫자는 법에, 스위치는 설정에

```python
# orders/rules.py
PAY_LINK_TIMEOUT = 60 * 60
```

법의 정본은 여기다 — 1시간이 2시간으로 바뀌면 `PAY-001@v2` 가 생긴다.
`config/settings.py` 의 `PAYMENT_LINK_TIMEOUT` 은 **관찰용 노브**이고,
환경변수를 준 때만 존재한다. 1시간을 기다리지 않기 위한 스위치다.

```bash
PAYMENT_LINK_TIMEOUT=5 just run
```

### 4. 만료는 이중 결제를 막지 않는다

**두 겹이 순서대로 걸린다.**

| 겹 | 무엇을 막나 | 어디서 |
|---|---|---|
| 토큰 | 오래된 링크 · 상태가 바뀐 주문의 링크 | `payment_token.check_token` → 409 `PAY-001@v1` |
| 계약 | 같은 순간 도착한 두 결제 중 하나 | `Order.mark_paid` 의 rowcount → 409 `ORDER-001@v1` |

토큰이 먼저 닫고, 계약이 마지막에 지킨다. 하나를 빼면 무엇이 뚫리는지는
제출물의 설명 문항이다. 두 탭에서 동시에 누르면 **토큰은 둘 다 통과한다** —
검사 시점에는 둘 다 `pending` 이기 때문이다. 거르는 것은 계약이다(테스트 13).

### 5. 나머지

- `config/urls.py` — `pay/<int:pk>/` → `pay/<int:pk>/<str:token>/`.
  비밀번호 흐름의 `uidb64` 자리에 주문 pk 가 들어간 모양이다.
- `orders/services.py:issue_payment_link` — URL 에 토큰 세그먼트를 붙이고
  `expires_at` 을 채운다. 판정 문장에 규칙 ID.
- `RULES.md` 2행 추가. `agent/prompts/ai_staff.md` 5·6번에 이사 표시
  (**6번은 부분 이사다** — 아래).

## 검증

```bash
just test 06     # 15개 전부
uv run pytest    # 0~5단계·실접속·403 도 그대로
```

손으로도 본다.

| 해 보는 것 | 이사 전 | 이사 후 |
|---|---|---|
| 시크릿 창에서 `bob` 으로 alice 의 링크 열기 | 200 — 주소·금액이 다 보인다 | **404** |
| `PAYMENT_LINK_TIMEOUT=5 just run` 뒤 5초 기다렸다 열기 | 200 | **409** `PAY-001@v1` · "AI 직원에게 새 결제 링크를 요청한다" |
| 결제를 끝낸 뒤 같은 링크 다시 열기 | 200(누르면 그때 409) | **409** `PAY-001@v1` · **대안이 다르다** — "주문 내역에서 현재 상태를 확인한다" |

마지막 행이 요점이다. 같은 규칙 ID, 같은 상태 코드, **다른 대안.**
없는 길을 적지 않는다는 4단계 규율이 여기서 분기로 나타난다 — 이미 결제된
주문에 "새 링크를 요청하라"는 대안이 아니라 헛걸음이다.

## 이 단계의 한 문장

> **링크는 열쇠가 아니다. 열쇠는 "누구"와 "언제"를 함께 묻는다.**

## 이 단계가 보장하지 않는 것

| 못 막는 것 / 안 하기로 한 것 | 지금 일어나는 일 | 어디서 |
|---|---|---|
| **AI 직원의 대행 스코핑** | `list_orders`·`get_order` 에 여전히 **모든 고객의 주문**이 나온다. 프롬프트 6번은 **부분 이사**이고, 이사 표시에 `미이사` 라고 적혀 있다. 표시 없는 문장만 부채인 것이 아니라 **부분 이사의 남은 반쪽도 부채**다 | 8단계 — 세계 부채 리포트 첫 항목 |
| 재고 예약 | 링크가 사는 1시간 동안 재고를 잡지 않는다. 한정판 1개에 링크 둘을 발급하면 늦은 쪽은 결제 페이지에서 `InsufficientStock` → **500**(5단계 표 그대로, 이제 사람이 본다) | 8단계 — 운영 |
| 링크 발급·사용 장부 | 누가 언제 발급했는지, 어떤 링크로 결제됐는지 **아무 데도 안 남는다**. 무상태 토큰의 대가다 | 7단계 — `paid_at` 과 함께 |
| Referer 로 토큰 누출 | `PasswordResetConfirmView` 의 세션 리다이렉트를 하지 않았다. 결제 페이지에 외부 링크가 없다는 것에 기대고 있다 | 8단계 — 운영 |
| 링크 취소 · 재발급 시 옛 링크 무효화 | 없다. 상태가 바뀌기 전까지 옛 링크도 산다(1시간 안이면). 정책 미정 | 고르지 않은 정책 |
| 결제 완료 푸시 | 없다. `get_order` 폴링이다 — 승인 핸들과 같다 | 8단계 |
| 주입 페이로드 재현 | 상품 설명에 `[시스템 지시]` 를 심고 fixture AI 가 따르는지 보는 축은 6단계에서 뺐다(설계서 §3 정정 블록). 이 세계의 AI 직원은 가게 직원이라 모든 주문을 보는 것이 자리에 맞고, 대화별 대행 주체가 아직 세계에 없다 | 8단계 |

## 실접속으로 같은 것을 보기

패키지 문(`itda-world-pkg`)으로:

> "SEED-0004 결제 처리해 줘"

`pay_order` 가 **격상**으로 답한다. 볼 것: 모델이 `handle.url` 을 안내하는가,
아니면 "결제를 완료했습니다"라고 말하는가.

링크를 **SEED-0004 의 주문자 `bob`** 으로 연다 → 결제된다.
`alice` 로 열면 **404** 다 — 그것도 관찰이다.

> "결제됐는지 확인해 줘"

`get_order` 가 `status: paid` 를 돌려준다. **푸시는 없다 — 물어봐야 안다.**

> "SEED-0002 다시 결제해 줘"

도구 오류 `ORDER-001@v1`. 링크조차 나가지 않는다.

HTTP 문(`itda-world`)으로 같은 것을 하면 202 를 `_escalated` 가 **환불 기준으로**
조립해 `refund_id: null` 이 나온다 — 관찰 2026-09-06 발견 1 의 재확인이다.
임시 서버는 손대지 않는다(8단계에서 대체).
자세한 것은 [`live-실접속.md`](live-실접속.md) (b)④ · (a') 표.

`stages/제출물/06-<본인이름>.md` 로 만들어 낸다.

### 2. 이사 비용 — 한 줄

[단계 색인의 이사 비용표](README.md#이사-비용표--법-하나의-원가를-줄-수로)에 있는

### 3. 설명

> **결제 링크의 만료와 `ORDER-001` 전이 계약은 각각 무엇을 막는가?
> 하나를 빼면 무엇이 뚫리는가?
> 그리고 `_make_hash_value` 에 `updated_at` 을 넣으면 왜 안 되는가.**
