실접속은 단계가 아니라 **병행 트랙**이다. 채점표가 없고(채점은 계속 고정 fixture),

진짜 Claude 를 붙여 **관찰**한다.

## 이사 비용표 — 법 하나의 원가를 줄 수로

세계에 법 하나를 심는 원가는 얼마인가. 단계마다 실측해 적는다.
두 가지를 **분리해서** 센다. 섞으면 "법을 켜는 데 든 코드"가 부풀려진다.

- **구현 diff** (`stage-NN-start` → `stage-NN-done`) — 학생이 실제로 쓰는 앱 코드.
  `*.py`·`*.html` 에서 `tests/`와 `migrations/`를 뺀 것.
- **준비 비용** (`stage-(NN−1)-done` → `stage-NN-start`) — 교재를 만드는 쪽이 미리
  깔아 두는 것. 채점 테스트·지시서·시작 상태에 심는 fixture(악성 카드 등)다.
  학생의 diff 에는 안 보이지만 **없으면 그 단계가 성립하지 않는다.**

### 재현 명령

표의 숫자는 아래로 다시 뽑을 수 있다. 손으로 센 값이 아니다.

```bash
# 구현 diff(앱 코드) — tests/ 와 migrations/ 를 뺀 *.py·*.html
git diff --numstat stage-04-start stage-04-done -- '*.py' '*.html' \
  | grep -v -e '^.*\ttests/' -e 'migrations/' \
  | awk '{a+=$1; d+=$2; n++} END {print n"파일 +"a" -"d}'

# 마이그레이션
git diff --numstat stage-04-start stage-04-done -- '*/migrations/*'

# 준비 비용 — 이전 단계 done 에서 이 단계 start 까지
git diff --numstat stage-03-done stage-04-start
```

**5단계의 준비 비용은 태그 기준으로 재면 안 된다.** `stage-04-done` 과
`stage-05-start` 사이에 실접속(live) 트랙 커밋 4개가 끼어 있어서, 태그로 재면
29파일 +3744 −55 가 나오고 그 대부분은 5단계와 무관한 토큰 API·MCP 서버·`uv.lock`
이다. 병행 트랙은 단계 비용이 아니므로 실접속 직전 커밋을 기준으로 잰다.

```bash
git diff --numstat a0c0710 stage-05-start     # 11파일 +1054 −3
```

### 분류별 재현 명령 — 다섯 갈래를 각각 센다

`stage-05-done` 총계 표의 다섯 행은 아래로 그대로 나온다. `TAGS` 만 바꿔 다른
단계에도 쓴다.

```bash
TAGS="stage-05-start stage-05-done"
sum() { awk '{a+=$1; d+=$2; n++} END {print n"파일 +"a" -"d}'; }

# 학생 앱 코드 — tests/·migrations/·management/commands/(채점 도구)를 뺀 *.py·*.html
git diff --numstat $TAGS -- '*.py' '*.html' \
  | grep -v -e '^.*\ttests/' -e 'migrations/' -e 'management/commands/' | sum

git diff --numstat $TAGS -- '*/migrations/*' | sum      # 마이그레이션
git diff --numstat $TAGS -- 'tests/*' | sum             # 채점표
git diff --numstat $TAGS -- 'orders/management/commands/*' | sum   # 채점 도구
git diff --numstat $TAGS -- '*.md' | sum                # 문서 (이 색인 포함)
git diff --numstat $TAGS | sum                          # 전체
```

4단계까지의 표는 `management/commands/` 를 앱 코드에서 빼지 않았다 — 그 단계에는
채점 도구가 없어서 결과가 같다. 5단계부터는 `just race` 가 생겨 갈린다.

`--stat` 대신 `--numstat` 을 쓰는 이유는 분류해서 합칠 수 있기 때문이다.
2·3단계처럼 `-start` 태그가 없는 단계는 `stage-(NN−1)-done`이 시작 상태다.

### 4단계 — 이사 비용

> **프롬프트 세 문장을 코드로 옮기는 데 앱 코드 5파일 · 376줄 추가 · 61줄 삭제
> + 마이그레이션 1개(18줄)가 들었다.**

새로 생긴 것: `orders/verdict.py`(판정 계약·결과) · `orders/rules.py`(임계값·규칙 ID) ·
`agent/templates/agent/denied.html`(409 화면). 고친 것: `orders/models.py` · `agent/views.py`.

숫자를 읽을 때 조심할 것.

- **LOC 는 변경량이지 시간·유지비·효율의 증명이 아니다.** "270줄이니 싸다/비싸다"는
  이 표가 답할 수 있는 질문이 아니다. 이 표가 답하는 것은 하나다 —
  *자연어 세 문장을 시행 코드로 바꾸는 데 든 변경량은 얼마인가.*
- 그 코드가 **어디까지** 지켜 주는지는 줄 수가 아니라 `RULES.md` 의
  "적용 경로 / 우회 가능 경로" 열이 답한다. 애플리케이션 검증은 지정 경로를
  지날 때만 시행된다 — DB 제약(3단계)과 다르다.
- 2·3단계의 구현 diff 0줄도 같은 표에 있어야 의미가 산다 —
  **이미 켜져 있던 법을 알아보는 데 드는 코드는 0줄이고, 교재 비용은 0이 아니다.**

### 5단계 — 이사 비용

> **"한 주문에 환불은 한 번이다" 한 문장을 세계에 심는 데 앱 코드 10파일 ·
> 439줄 추가 · 61줄 삭제 + 마이그레이션 1개(33줄)가 들었다.**

4단계(376/61)보다 조금 크고 **성격이 다르다.** 4단계는 프롬프트에만 있던 문장을
코드로 옮긴 것이고, 5단계는 코드에 이미 있던 방어(`filter().first()`)의 **역할을
바꾼** 것이다 — 막는 일은 DB 제약에 넘기고, 조회는 "이미 답이 있는 질문에 답하는"
자리로 옮겨 판정 앞에 세웠다. 삭제 61줄 안에 서비스 층의 사전 조회와 API 의 사전
상태 검사가 들어 있다.

새로 생긴 것: `config/middleware.py`(잠금 실패 → 503). 고친 것:
`orders/models.py`(제약·`apply` 순서·전이 계약, 194/26 으로 가장 크다) ·
`orders/api.py`·`admin.py`·`views.py`(세 부름터가 `InvalidTransition` 을 받는다) ·
`orders/verdict.py`(`REPLAYED`·`from_dict`) · `agent/live/mcp_server.py`(`request_id`).

준비 비용이 처음으로 구현 diff 를 크게 넘는다(+1054 대 +368). 경합을 **재현
가능하게** 만드는 값이다 — 파일 테스트 DB, Barrier 헬퍼, 그리고 눈으로 보는
`just race` 명령 268줄. 경합은 "그냥 두 번 호출"로는 관찰되지 않는다.

**법 하나에 시행 면이 셋인 것은 자동으로 나온 결과가 아니다.** 무엇이 "같은
사건"인가, 거부 뒤의 새 제안은 중복인가, 열쇠는 재사용되는가 — 셋 다 원문 한
줄에서 연역되지 않는 **정책 선택**이고, 그래서 `RULES.md` 의 "적용 경로" 열이
길다. 줄 수는 그 선택의 값이지 문장의 값이 아니다.

### 6단계 — 이사 비용

> **"결제는 고객이 한다" 와 "고객의 주문은 그 고객에게만" 두 문장을 세계에 심는 데
> 앱 코드 5파일 +189 −19 이 들었다. 마이그레이션은 0개다.**

**마이그레이션 0 이 이 단계의 성질이다.** 6단계는 모델을 하나도 건드리지 않는다 —
결제 링크는 **무상태**(서명 토큰)이고 소유권은 이미 `Order.user` 에 있다.
`PaymentLink` 모델을 두는 설계도 가능했지만 그건 7단계 장부를 앞당기는 것이라
기각했다(`docs/사양-06-주체.md` §8). 법을 켜는 데 스키마가 늘 필요하지는 않다.

**준비 비용이 구현 diff 를 크게 넘는다**(5단계에 이어 두 번째다). 이유는 하나다 —
**고객의 문이 통째로 새로 생긴다.** 로그인·결제 페이지·템플릿 둘·링크 발급 서비스·
API 와 도구와 콘솔 카드 ⑦ 까지가 전부 교재 쪽 비용이고, 학생이 쓰는 것은 그 위의
법 둘뿐이다. 설계 §3-2 의 두 축 분리가 가장 크게 벌어지는 자리다.

**패키지 선행 커밋이 따로 있다.** 승인 핸들이 "누른다" 에서 "연다" 로 일반화되는
변경(`django_itda/tools.py:Toolset._handle` — 도구가 `objects['handle']` 로 필드를
보탠다)은 저장소 루트의 `8b3a706`(django-itda v0.1.1)이고, 위 표의 준비 비용에는
들어 있지 않다(다른 패키지의 코드다). 이 단계가 패키지에 준 사양 입력의 값이다.

숫자를 읽을 때 조심할 것은 4·5단계와 같다. **LOC 는 변경량이지 효율의 증명이
아니다.** 두 법이 **어디까지** 지키는지는 `RULES.md` 의 "적용 경로 / 우회 가능
경로" 열이 답하고, `SCOPE-001@v1` 의 그 칸에는 **부분 이사**라고 적혀 있다.

## 태그 규약

- 단계마다 `stage-NN-start`(결함이 심어진 시작 상태)와 `stage-NN-done`(법이 켜진 완료 상태) 두 개.
- `stage-NN-done`은 곧 `stage-(NN+1)-start`와 같은 커밋일 수 있다. 그래도 태그는 둘 다 붙인다.
- 0단계만 예외 — 시작 상태가 빈 저장소라 `stage-00-start`가 없다.
- **코드 변경이 없는 단계는 `-done` 하나만 붙인다.** 해부·실측만 하는 단계(2·3단계)는
  애플리케이션 코드를 고치지 않으므로 시작 상태와 완료 상태의 앱 코드가 같다.
  그 단계의 테스트는 이전 단계 완료 상태에서 이미 통과한다 — 새 법을 켜는 것이 아니라
  이미 켜져 있던 법을 테스트로 붙잡아 두는 것이기 때문이다.
  이때 `stage-NN-start`는 만들지 않고, `stage-(NN-1)-done`이 그 자리를 대신한다.
- 히스토리 재작성 금지. 이전 단계 코드를 고쳐야 하면 **최신 커밋에서 고치고 태그만 옮긴다**.
- 태그를 옮기면 아래 이력 표에 반드시 한 줄 남긴다.
