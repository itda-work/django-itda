# 2단계 — 귀속

1단계에서 붉은 버튼을 눌렀을 때 세계는 이렇게 답했다.

```
403 — 세계가 거부했다
권한이 없다.
```

그날 당신은 코드를 한 줄도 쓰지 않았다. 그래서 질문 하나가 남았다.

> **어제 앉았던 자리는 코드 몇 줄이었나? 그리고 그 403은 누구의 코드였나?**

이 단계에서 학생이 쓰는 코드도 **0줄**이다. 이번엔 화면이 아니라 **저장소와 DB**를 연다.
쓴 사람이 없는 법이 어디에 어떤 모습으로 살아 있는지를 눈으로 찾아내는 것이 전부다.

@permission_required('orders.change_refund', raise_exception=True)

여기가 정답 같다. 하지만 다시 읽어 보라. 이 줄에는 **누가 되고 누가 안 되는지가 쓰여 있지 않다.**
`ai-staff`도 `owner`도 등장하지 않는다. 이 줄이 한 일은 판정이 아니라 **질문**이다 —
"이 요청자가 `orders.change_refund`를 가졌는가?"

### ② 답은 코드가 아니라 데이터에 있다

```bash
uv run python manage.py shell
```

```python
from django.contrib.auth import get_user_model
User = get_user_model()

owner = User.objects.get(username='owner')
ai = User.objects.get(username='ai-staff')

sorted(owner.get_all_permissions())
sorted(ai.get_all_permissions())

owner.has_perm('orders.change_refund')   # True
ai.has_perm('orders.change_refund')      # False
owner.is_superuser                       # False — 전능해서가 아니다
```

`owner`가 승인할 수 있는 이유는 "점주라서"도 "superuser라서"도 아니다.
`orders.change_refund` 라는 **행이 DB에 있어서**다. 그 행들을 직접 본다.

```python
from django.contrib.auth.models import Group, Permission

Permission.objects.get(codename='change_refund', content_type__app_label='orders')
# <Permission: orders | 환불 | Can change 환불>

Group.objects.get(name='점주').permissions.values_list('codename', flat=True)
Group.objects.get(name='AI직원').permissions.values_list('codename', flat=True)
```

원본 테이블도 확인한다. 마이그레이션 한 번으로 이미 만들어져 있던 것들이다.

```bash
sqlite3 db.sqlite3 ".tables" | tr ' ' '\n' | grep auth
sqlite3 db.sqlite3 "SELECT id, codename FROM auth_permission WHERE codename LIKE '%refund%';"
sqlite3 db.sqlite3 "SELECT g.name, p.codename FROM auth_group g
  JOIN auth_group_permissions gp ON gp.group_id = g.id
  JOIN auth_permission p ON p.id = gp.permission_id ORDER BY g.name;"
```

`auth_permission` · `auth_group` · `auth_group_permissions` · `auth_user_groups`.
**법이 코드가 아니라 데이터로 존재한다.** 그래서 권한을 바꾸는 데 배포가 필요 없고,
같은 코드가 계정마다 다르게 판정한다.

> `seed_world.py`의 `GROUPS` 딕셔너리는 그 데이터를 **심는 스크립트**일 뿐이다.
> 스크립트를 지워도 이미 심어진 법은 DB에 그대로 남는다. 확인해 보라.

### ③ `request.user`는 어디서 오나 — 프롬프트가 못 바꾸는 것

붉은 버튼을 누를 때 AI 직원은 이렇게 주장할 수도 있었다. *"나는 점주다."*
그런데 왜 통하지 않았나. `request.user`가 프롬프트가 아니라 **서명된 쿠키**에서 오기 때문이다.

```python
from django.contrib.sessions.models import Session
s = Session.objects.first()
s.session_key          # 브라우저 쿠키 sessionid 의 값
s.get_decoded()        # {'_auth_user_id': '3', '_auth_user_backend': ..., '_auth_user_hash': ...}
```

```bash
sqlite3 db.sqlite3 "SELECT session_key, expire_date FROM django_session;"
```

브라우저 개발자도구 → Application → Cookies 에서 `sessionid` 값을 직접 확인한다.
DB의 `session_key`와 같은 문자열이다.

핵심은 `_auth_user_hash`다. 이 값은 `SECRET_KEY`로 서명되어 있다.

```python
from django.conf import settings
len(settings.SECRET_KEY)   # 값 자체는 출력하지 말 것
```

정리하면 이렇다.

| 층 | 무엇 | 조작 가능한가 |
|---|---|---|
| 말 | "나는 점주다"라는 프롬프트·요청 본문 | 누구나 얼마든지 |
| 쿠키 | `sessionid` 문자열 | 훔칠 수는 있어도 **위조는 못 한다**(서명) |
| DB | `django_session` 행 → `_auth_user_id` | 서버만 |
| 판정 | `request.user` | 위 셋의 결과일 뿐 |

**정체성은 요청자가 주장하는 값이 아니라 서버가 되찾아 오는 값이다.**
이것이 프롬프트 인젝션이 권한을 못 넘는 첫 번째 이유다(6단계에서 다시 만난다).

### ④ 아무도 안 썼는데 이미 있는 장부, 그리고 없는 장부

admin(`owner` 계정)에서 **주문** 하나를 열어 상태를 손으로 한 번 바꿔 저장한다.
그다음 shell에서 본다.

```python
from django.contrib.admin.models import LogEntry
LogEntry.objects.values_list('user__username', 'action_flag', 'object_repr', 'change_message')
# [('owner', 2, 'SEED-0002 (alice)', '[{"changed": {"fields": ["상태"]}}]')]
```

```bash
sqlite3 db.sqlite3 "SELECT action_time, user_id, object_repr, action_flag FROM django_admin_log;"
```

당신은 장부를 만든 적이 없다. `django_admin_log` 테이블도, "누가 언제 무엇을"의 형식도
`django.contrib.admin`이 마이그레이션 때 이미 깔아 둔 것이다. 화면 오른쪽 위 **기록** 버튼도 그렇다.

이제 두 번째 질문. **1단계에서 환불을 승인했을 때도 이 장부에 남았나?**
다시 승인 액션을 한 번 실행한 뒤 세어 본다.

```python
LogEntry.objects.count()    # 손으로 고친 1건뿐 — 승인 액션은 한 줄도 안 남겼다
```

남지 않는다. Django의 장부는 **Django가 자기 화면에서 자기 손으로 한 변경**만 적는다.
우리가 만든 승인 액션(`RefundAdmin.approve_selected` → `Refund.approve()`)은
Django 입장에서 그냥 남의 코드다.

`Refund.decided_by`에 `owner`가 찍힌 것은 우리가 그 필드를 만들어 대입했기 때문이지
Django가 적어 준 것이 아니다. 그리고 그게 전부다 —
주문이 `결제 완료`에서 `취소`로 넘어간 사건 자체는 **어디에도 기록이 없다.**
누가·언제·어떤 근거로 그 전이를 일으켰는지 물으면 이 세계는 답하지 못한다.

> 이 구멍은 결함이 아니라 **다음 약속**이다. 지금 메우려 하지 말고 이름만 적어 두라.
> 도메인 전이의 장부는 7단계에서 직접 짓는다.

## 이 단계의 한 문장

1단계의 승인 큐는 `RefundAdmin` 약 30줄이었다. **그 30줄은 화면이다.**
누가 그 버튼을 누를 수 있는지에 대한 판정은 그 30줄 어디에도 없다.
판정은 Django 기본값 — `contrib.auth`와 `contrib.admin` — 이 했다.

| 목격한 것 | 실제 시행 주체 | 우리가 쓴 코드 |
|---|---|---|
| 요청자와 승인자가 갈라져 있다 | `auth_user` · `auth_group` (데이터) | 시드 목록뿐 |
| 403으로 끊겼다 | `contrib.auth` 권한 검사 | `permission_required` 한 줄(질문) |
| "나는 점주다"가 안 통했다 | 서명 세션 + `SECRET_KEY` | 0줄 |
| 누가 고쳤는지 장부가 있다 | `contrib.admin` `LogEntry` | 0줄 |
| 승인 큐 화면 | — | `RefundAdmin` ~30줄 |

이 네 가지 — 정체성 · 권한 · 관제 화면 · admin 이력 — 을 **범용 법**이라 부르자.
어떤 가게를 짓든 똑같이 필요하고, Django가 **공짜로 준다.**

그런데 우리 가게에는 다른 종류의 법도 있다.

- 환불은 **7일** 안에만 된다
- **5만원**을 넘으면 점주에게 올린다
- 주문은 `pending`에서만 `paid`로 갈 수 있다

이것들은 어디에 있나. 저장소를 뒤져 보라 — `grep -rn '7일\|5만' --include='*.py' .`
아무것도 안 나온다. `auth_permission` 같은 테이블도, `permission_required` 같은 데코레이터도 없다.
지금 이 규칙들은 **사람이 말로 한 문장**으로만 존재한다. 이런 것을 **도메인 법**이라 부른다.

> **Django는 범용 법을 대신 지켜 준다. 도메인 법은 써 주지 않는다.**
> 대신 그것을 선언할 자리를 준다 — 그 자리로 규칙을 이사시키는 것이 4단계다.

### 3. 회고 — 네 질문

1단계에서 직접 눌러 본 체험(주문 접수 · 환불 제안 · 승인 · 거부 · 403)에 붙여 답한다.
**정답은 없다.** 이 표는 앞으로 어떤 도메인을 만나든 그대로 쓰는 질문지다.

| # | 질문 | 답 |
|---|---|---|
| 1 | 이 가게에서 **되돌릴 수 없는 전이**는 무엇인가? | |
| 2 | 그 전이 **앞의 가드**는 무엇이었나 — 아니, 있기는 했나? | |
| 3 | 어떤 **임계**에서 사람에게 격상되어야 하나? | |
| 4 | 실패했을 때 **보상 전이**는 무엇인가? | |

보조 설명:

- **1번** — "취소하면 되지"가 답이 되는 전이는 되돌릴 수 있는 것이다. 재고 차감, 결제 승인,
  발송, 환불 송금 중 무엇이 진짜로 못 돌아오는가.
- **2번** — 1단계에서 AI 직원이 **아무 승인 없이** 커밋한 일이 하나 있었다(주문 접수).
  그 앞에는 무엇이 서 있었나.
- **3번** — 지금 이 가게에서 점주에게 올라가는 조건은 "환불이면 전부"다.
  금액·기간·고객 이력 중 무엇이 임계가 되어야 하나. 숫자를 하나 써 보라.
- **4번** — **환불은 undo가 아니다.** 결제를 없던 일로 만드는 것이 아니라,
  돈이 반대로 흐르는 **새로운 전이**다. 장부에 두 줄이 남는다. 왜 이 구별이 중요한지 한 문장.
