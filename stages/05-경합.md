# 5단계 — 경합

4단계 마지막 문장을 들고 왔다.

> 오늘 쓴 rowcount 판정이 5단계에서 다시 나온다.

다시 나오기는 하는데, **한 번은 버티고 한 번은 못 버틴다.** 이번 단계는 그 차이를
보는 곳이다. 그리고 그 차이 때문에, 처음으로 법을 **DB 제약**으로 내려 놓는다 —
3단계에서 "전부 지켜지는 층"이라고 이름만 붙여 놓았던 그 칸이다.

## 준비 — 4단계가 못 막는다고 적어 둔 것들

```bash
just reset-db
cat agent/prompts/ai_staff.md
```

문장이 하나 늘었다.

> 4. **같은 환불을 두 번 처리하지 마라. 한 주문에 환불은 한 번이다.**

이사 표시가 없다. 아무도 안 지켜 준다는 뜻이다.

4단계 지시서의 [「이 단계가 보장하지 않는 것」](04-규칙의-이사.md#이-단계가-보장하지-않는-것)
표에서 "5단계"라고 적어 둔 행을 다시 읽는다. 넷이다.

| 못 막는 것 | 4단계가 적어 둔 지금 일어나는 일 |
|---|---|
| 같은 주문에 환불 두 번 신청 | 승인된 환불이 두 개 생긴다(콘솔이 걸러 줄 뿐) |
| 동시에 들어온 두 제안 | 둘 다 승인될 수 있다. 잠그지 않는다 |
| 승인 시점의 기한 재검사 | 신청 때만 본다 |
| DB 잠금 실패 | `OperationalError` 가 그대로 올라간다 |

이 중 셋은 오늘 막는다. 하나(승인 시점 기한 재검사)는 **막지 않기로 정한다** —
왜 안 막는지도 오늘의 내용이다.

## 명령 — 같은 요청 두 개를 동시에 쏜다

이번 단계의 도구는 콘솔 카드가 아니다. 같은 요청 두 개를 **정확히 같은 순간에**
출발시키는 명령이다.

```bash
just race refund SEED-0003 --amount 30000
```

```
[A] 200 ALLOW  COMMITTED · 기한 안(1일 경과)이고 50,000원 이하다 …
[B] 200 ALLOW  COMMITTED · 기한 안(1일 경과)이고 50,000원 이하다 …
```

**승인된 환불이 두 건이다.** 한 주문에 3만원씩 두 번 나갔다. 확인해 본다.

```bash
uv run python manage.py shell -c "from orders.models import Refund; print(list(Refund.objects.values_list('order__order_number','status','amount')))"
```

이번엔 결제다.

```bash
just race pay SEED-0004
```

```
[A] 200 ALLOW  SEED-0004 을(를) 결제 완료로 옮겼습니다.
[B] 409 DENY [ORDER-001@v1]  ORDER-001@v1: 결제 대기 상태가 아니다(조건 불일치). …
```

**이건 버틴다.** 한정판 재고 1개도 한 번만 깎였다.

채점표도 같은 말을 한다.

```bash
just test 05     # 11개 중 3개만 통과한다 (8 failed, 3 passed)
```

통과하는 셋 중 하나가 `test_동시_결제_두_개_중_하나만_통과한다_HTTP` 다.
4단계에서 못 했던 **경합의 증명**을 오늘은 할 수 있고, 4단계 계약은 그 증명을 통과한다.

## 의도적 실패 — 왜 결제는 버티고 환불은 못 버티는가

두 요청의 모양이 다르다.

- 결제는 **UPDATE** 다. `WHERE status = 'pending'` 을 걸 **행이 이미 있다.**
  두 스레드가 같은 행에 조건부 UPDATE 를 쏘면 DB 가 줄을 세우고, 진 쪽은
  rowcount 0 을 받는다. 4단계에 심은 계약 그대로다.
- 환불 제안은 **INSERT** 다. 아직 아무 행도 없다. **조건을 걸 대상이 없다.**

그럼 4단계는 중복을 어떻게 막고 있었나. `orders/services.py` 를 연다.

```python
existing = Refund.objects.filter(order=order).exclude(status=Refund.Status.REJECTED).first()
if existing:
    return existing.current_outcome()
return Refund.apply(...)
```

**조회하고, 없으면 만든다.** 이름이 있는 패턴이다 — *check-then-act*.
두 요청이 순서대로 오면 잘 동작한다. 동시에 오면 **둘 다 조회를 통과한다.**
조회와 생성 사이에 벌어진 그 틈이 오늘의 자리다. 4단계 주석에 이미 적혀 있었다 —
"세계가 중복을 막아 주는 것이 아니다. 여기서 걸러 줄 뿐이고, 그 얘기는 5단계다."

확정 쪽에도 같은 틈이 있다. `orders/api.py:refund_approve` 를 연다.

```python
if refund.status != Refund.Status.PROPOSED:
    ...
refund.approve(request.user)
```

역시 **조회하고 나서 쓴다.** 그리고 `Refund.approve` 자체는 조건 없는 `save()` 다.
`reject()` 도 마찬가지다 — 이미 승인된 환불을 거부로 **덮어쓴다.** 그러면 주문은
취소된 채로 환불은 '거부'가 되고, 장부가 거짓말을 한다.

```bash
just race approve <환불 ID>     # 둘 다 200 이다
```

마지막으로 하나 더. 잠금 실패다.

> 세계가 잠겨서 판정하지 **못한** 것과, 판정해서 **거부한** 것은 다른 사건이다.

지금은 `OperationalError` 가 그대로 올라가 **500** 이 된다. AI 직원이 500 을 받으면
무엇을 해야 하는지 알 수 없다. 다시 보내야 하는가, 포기해야 하는가.

## 수정 — 세 개의 경합, 세 개의 도구

법은 **하나**다.

> `REFUND-003@v1` — 같은 환불을 두 번 처리하지 마라. 한 주문에 환불은 한 번이다.

시행 면이 셋인 이유는 경합의 모양이 셋이기 때문이다. 한 문장의 세 얼굴이다.

| 경합의 모양 | 막는 것 | Django 가 준 자리 |
|---|---|---|
| 다른 두 요청이 같은 주문에 환불을 만든다 (INSERT) | 살아 있는 환불은 주문당 하나 | `UniqueConstraint(condition=…)` → `IntegrityError` |
| 같은 요청이 두 번 온다 (재전송) | 같은 열쇠는 같은 답 | `UniqueConstraint(order, idempotency_key)` + 저장해 둔 판정 |
| 점주 둘이 동시에 확정한다 (UPDATE) | 확정은 제안 상태에서만 | 4단계 모양 그대로 — 조건부 UPDATE + rowcount |

순서대로 심는다.

### 1. 제약 — `orders/models.py:Refund.Meta`

```python
constraints = [
    models.UniqueConstraint(
        fields=['order'],
        condition=Q(status__in=['proposed', 'approved']),
        name='refund_one_live_per_order',
    ),
    models.UniqueConstraint(
        fields=['order', 'idempotency_key'],
        condition=~Q(idempotency_key=''),
        name='refund_idempotency_key_per_order',
    ),
]
```

**부분** 유일이라는 점이 중요하다. `fields=['order']` 만 걸면 거부된 건이 있는
주문에는 영영 환불을 못 올린다. 거부는 사건의 **끝**이고, 그 뒤의 새 제안은
같은 환불의 중복이 아니라 **다른 사건**이다. 조건절이 그 정의를 담는다.

두 번째 제약의 `~Q(idempotency_key='')` 도 같은 종류의 판단이다. 열쇠를 안 준
요청 둘을 "같은 요청"이라고 부를 근거가 없으므로, 빈 열쇠는 제약 밖에 둔다.

이건 3단계의 `CHECK ("stock" >= 0)` 와 **같은 층**이다. 확인해 본다.

```bash
uv run python manage.py shell -c "
from orders.models import Refund, Order
o = Order.objects.get(order_number='SEED-0003')
Refund.objects.create(order=o, amount=1, reason='shell', status='approved')
Refund.objects.create(order=o, amount=1, reason='shell 두 번째', status='approved')
"
```

`IntegrityError`. 서비스 함수도, 판정도, 뷰도 지나지 않았는데 걸렸다.
4단계의 세 법은 여기서 아무것도 못 했다.

### 2. `Refund.apply` — 뒤집기

이 단계의 핵심 한 줄이다.

```python
# 4단계 — check-then-act
existing = Refund.objects.filter(order=order).exclude(status=REJECTED).first()
if existing:
    return existing.current_outcome()
return Refund.apply(...)

# 5단계 — act-then-check
try:
    with transaction.atomic():
        refund = cls.objects.create(...)
        ...
except IntegrityError as collision:
    return cls._resolve_collision(order, idempotency_key, collision)
```

**물어보고 쓰지 말고, 쓰고 나서 물어라.** 물음을 DB 에 맡긴 것이다. 조회와
생성 사이의 틈은 애플리케이션이 없앨 수 없지만, INSERT 한 방에는 틈이 없다.

두 가지를 지킨다.

- `IntegrityError` 는 **`atomic()` 블록 바깥에서** 잡는다. 안에서 잡고 계속
  쓰면 이미 깨진 트랜잭션 위에 쿼리를 날리게 된다.
- 걸린 이유를 **모르면 삼키지 않는다.** 같은 열쇠 행도 없고 살아 있는 환불도
  없는데 제약에 걸렸다면 그건 우리가 모르는 실패다. 모르는 실패를 도메인 답으로
  번역하는 순간부터 세계가 거짓말을 시작한다.

`_resolve_collision` 의 두 갈래가 곧 두 개의 결과값이다.

| 상황 | 돌려주는 것 | `Outcome` |
|---|---|---|
| 같은 열쇠의 행이 있다 | 그때 저장해 둔 판정 | `REPLAYED` |
| 살아 있는 환불이 있다 | 지금 상태 | `ALREADY` |

### 3. `Refund.approve` / `reject` — 4단계 모양 그대로

```python
moved = Refund.objects.filter(pk=self.pk, status=Status.PROPOSED).update(...)
if not moved:
    raise InvalidTransition(...)
```

`Order.mark_paid` 와 한 글자도 다르지 않은 모양이다. 그리고 4단계의 규율도
그대로 따른다 — 거부 사유에 `self.status` 를 찍지 않는다. 재조회하지 않은
메모리 위의 값을 DB 의 현재 상태인 양 말할 수 없다.

부르는 쪽 셋이 이 예외를 받는다.

| 부르는 곳 | 받으면 |
|---|---|
| `orders/views.py` (콘솔) | `messages.warning` + 되돌아가기 |
| `orders/admin.py` (승인 큐 액션) | `n건 승인, m건은 제안 상태가 아니어서 건너뜀` |
| `orders/api.py` (JSON) | **409** + `rule_ids: ['REFUND-003@v1']` |

`orders/api.py:refund_approve` 에서 **`status != PROPOSED` 사전 검사를 지운다.**
그 세 줄이 4단계에 남아 있던 check-then-act 였다.

### 4. 멱등키 입구 — `orders/api.py`

`Idempotency-Key` 헤더를 먼저 보고, 없으면 본문의 `idempotency_key` 를 본다.
멱등키는 요청 **내용**이 아니라 요청 **자체**에 붙는 표찰이라 헤더가 제자리다.

응답의 상태 코드는 손대지 않는다. `REPLAYED` 면 저장된 판정을 그대로 들고
오므로 `verdict.status_code` 가 처음 응답과 같아진다 — 재전송이 처음과 같은
답을 받는다는 것은 본문뿐 아니라 **상태 코드까지** 같다는 뜻이다.

MCP 도구에도 같은 열쇠 구멍을 낸다. `propose_refund(..., request_id=...)` 가
그 값을 헤더로 옮긴다.

### 5. 잠금 실패는 판정이 아니다 — `config/middleware.py`

```python
def process_exception(self, request, exception):
    if not isinstance(exception, OperationalError):
        return None
    ...  # 503 + Retry-After: 1
```

- **409 로 만들면 안 된다.** 규칙 위반이 아닌데 규칙 위반이라고 답하는 것이다.
- **500 으로 두어도 안 된다.** 받은 쪽이 재시도해도 되는지 알 수 없다.
- 본문에 `kind`·`rule_ids` 를 싣지 않는다. **판정한 적이 없기 때문이다.**

`OperationalError` 가 아니거나 메시지에 `locked`·`busy` 가 없으면 손대지 않는다.
500 은 500 이다.

설정도 함께 만진다.

```python
'OPTIONS': {'transaction_mode': 'IMMEDIATE', 'timeout': 5,
            'init_command': 'PRAGMA journal_mode=WAL;'}
```

**이건 완화이지 보장이 아니다.** 잠금 실패의 빈도를 줄일 뿐 없애지 못한다.
없앨 수 없는 것을 정직하게 말하는 응답이 보장이다.

### `select_for_update` — 잠갔다고 믿는 잠금

경합이라고 하면 제일 먼저 떠오르는 것이 잠금이다. 써 본다.

```python
with transaction.atomic():
    Order.objects.select_for_update().filter(status='paid')
```

오류도, 경고도 없다. 그런데 **아무것도 안 잠긴다.**

```python
connection.features.has_select_for_update   # False
```

Django 는 백엔드가 지원할 때만 `FOR UPDATE` 를 붙인다. SQLite 는 지원하지
않으므로 평범한 SELECT 가 나간다. 코드는 잠갔다고 말하고 있고, 세계는 안 잠갔다.

PostgreSQL 이면 진짜 행 잠금이 걸린다. 그건 여기서 확인할 수 없다 —
이 과정은 8단계까지 외부 서비스 0 이다. 그래서 오늘 배우는 것은
"어느 잠금을 쓰나"가 아니라 **"내가 쓴 보장이 실제로 켜져 있는지 확인하는 법"**이다.

## 이 단계의 한 문장

> **물어보고 쓰지 마라. 쓰고 나서 물어라.**

check-then-act 를 act-then-check 로 뒤집은 것이고, 그렇게 할 수 있는 이유는
"물음"을 DB 에 맡겼기 때문이다. 4단계에서 rowcount 로 배운 것과 같은 종류의
발상인데, 이번에는 조건을 걸 행이 없어서 **제약**이라는 다른 도구를 썼다.

그리고 4단계의 관통 문장에 한 겹이 붙는다.

> 제안은 AI, 판정은 세계, 확정은 사람. 그리고 **같은 사건은 두 번 일어나지 않는다.**
> 재시도는 새 사건이 아니고(멱등키), 경합의 패자는 거짓말 없이 "이미 있다"를 듣는다.

## 이 단계가 보장하지 않는 것

| 못 막는 것 / 안 하기로 한 것 | 지금 일어나는 일 | 어디서 |
|---|---|---|
| 승인 시점의 기한 재검사 | **정책으로 확정: 하지 않는다.** 판정 시점은 신청 시점이다. 기한은 사건의 성질이지 경합이 아니다 | 바꾸려면 `REFUND-001@v2` — 새 행이 필요한 운영 판단이다 |
| 실제 잠금 실패의 재현 | 채점하지 않는다(환경 의존). 503 은 **주입** 테스트로만 확인한다. `IMMEDIATE`·`timeout`·WAL 은 빈도를 줄일 뿐 없애지 못한다 | — |
| 재고 마지막 1개를 **다른 두 주문**이 동시에 결제 | `stock__gte` 조건부 UPDATE(0단계 범용 법 + 4단계)가 막는다. 여기서는 실측하지 않았다 | 실접속 관찰 소재 |
| DENY 재전송 | DENY 는 저장하지 않으므로 다시 판정한다. 같은 입력이면 같은 답이지만, 7일 경계를 넘긴 재전송은 답이 바뀐다 | 의도된 것 |
| 멱등키의 만료·정리 | 없다. 영원히 남는다 | 8단계 — 운영 |
| 누가 재전송했는가 · 경합의 패자가 누구였는가 | 아무 데도 안 남는다. 결과 상태로만 짐작한다 | 7단계 — 궤적 |
| 남의 주문에 환불을 거는 것 | 소유권 스코핑이 없다 | 6단계 — 주체 |

## 실접속으로 같은 것을 보기

Claude 창을 **둘** 띄우고 같은 말을 동시에 시킨다.

> "SEED-0003 을 3만원 환불해 줘"

하나는 확정되고 하나는 "이미 있다"를 듣는다. 둘 다 성공했다고 말하지 않는다.

같은 창에서 두 번 시키면 도구가 `request_id` 를 붙였는지에 따라 갈린다 —
붙였으면 `outcome: REPLAYED`(그때의 답), 안 붙였으면 `ALREADY`(지금 상태).
**둘 다 정직한 답이고, 둘은 다른 답이다.**

옆자리 학생과 해 보려면 세계를 열어야 한다.

```bash
just run-shared                                  # 0.0.0.0 바인드 + WORLD_SHARED=1
just race refund SEED-0003 --http --url http://<상대 IP>:8000 --rounds 10
```

`--http` 는 **확률적**이다. 겹치는 창이 좁아 매번 경합하지 않는다. 그래서 회차를
반복하고, 겹친 회차에서만 `ALREADY` 가 나온다. in-process 모드(`--http` 없이)가
매번 겹치는 것과 비교해 보면, **경합은 드물게 일어나고 드물다고 안 일어나는 것은
아니다**라는 것이 눈에 보인다.

`WORLD_SHARED=1` 이 여는 것은 호스트 검사까지다. 학생별 계정과 소유권 스코핑은
6단계의 몫이다.
