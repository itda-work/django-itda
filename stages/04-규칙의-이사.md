# 4단계 — 규칙의 이사 ★

3단계 마지막 질문을 들고 왔다.

> 재고에는 `CHECK ("stock" >= 0)` 가 있었다. **그럼 주문 상태에는?**

이번 단계는 이 과정의 심장이다. 여기서 처음으로 **도메인 법**을 옮긴다.
지금까지 본 법(권한·세션·`PositiveIntegerField`)은 Django가 딸려 준 것이었다.
이번 것은 아무도 안 써 준다. 우리 가게에만 있는 법이기 때문이다.

## 준비 — 우리 가게의 법은 지금 어디에 있는가

```bash
just reset-db
cat agent/prompts/ai_staff.md
```

세 문장이 보인다.

1. 결제 후 7일이 지난 주문은 환불하지 마라.
2. 5만원을 초과하는 환불은 반드시 점주 승인을 받아라.
3. 이미 결제 완료된 주문을 다시 결제 완료로 만들지 마라.

이것이 우리 가게의 도메인 법 전부다. 그리고 지금 이 법이 사는 곳은
**대화 맨 앞에 붙는 텍스트 파일 한 개**다.

정확히 말하면 시작 상태는 **일부만 코드화된** 세계다. 코드를 열어 보면
5만원 임계는 이미 들어가 있다(`Refund.auto_or_escalate()` 의 금액 한 줄).
반면 **7일 기한과 주문 상태 검사는 프롬프트에만 있다.** 그러니까 이 단계에서
실제로 이사하는 것은 "아무것도 없는 곳에 법 세 개"가 아니라
**반쯤 걸쳐 있는 법을 제자리로 옮기고, 빠진 두 개를 새로 심는 일**이다.

3단계에서 만든 표를 다시 꺼내 본다.

| 법이 사는 층 | 지켜지는 범위 |
|---|---|
| 프롬프트 | AI가 협조할 때만 |
| … | … |
| DB 제약 | 전부 |

우리 세 문장은 맨 윗칸에 있다. 그럼 AI가 협조하지 않으면 어떻게 되는가.
말로 물어보지 말고 **눌러서 확인한다**.

## 명령 — 악성 카드 두 장

콘솔에 카드가 두 장 늘었다(⑤⑥). 빨간 테두리다.
AI 직원이 프롬프트를 어기는 응답을 냈다고 가정한 **고정 fixture**다.
확률이 아니다 — 누를 때마다 똑같이 어긴다. 각 카드 안에 그것이 어기는
프롬프트 문장이 인용돼 있다.

```bash
just run       # http://127.0.0.1:8000/agent/ 에 ai-staff / ai1234 로 로그인
```

**⑤ 8일 지난 주문 환불** — `SEED-0001`은 8일 전 주문이다. 프롬프트 1번이 금지한다.
금액은 22,500원이라 5만원 임계 아래다.

**⑥ 결제 완료 주문 재결제** — `SEED-0002`는 이미 `paid`다. 프롬프트 3번이 금지한다.
누르기 전에 재고를 적어 둔다.

```bash
uv run python manage.py shell -c "from shop.models import Product; print(Product.objects.get(name='만년필 잉크 30ml').stock)"
```

## 의도적 실패 — 서버가 허용한다

⑤를 누른다.

```
세계가 허용했다 ⚠️ — SEED-0001 환불 22,500원이 자동 승인되었습니다.
주문은 취소 로 바뀌었습니다. 아무도 이 요청을 검사하지 않았습니다.
```

8일이 지난 주문이 환불됐다. 점주는 아무것도 누르지 않았다.

⑥을 누른다.

```
세계가 허용했다 ⚠️ — SEED-0002 를 다시 결제 처리했습니다.
주문 상태는 결제 완료 그대로인데 재고는 30 → 27 로 또 깎였습니다.
```

상태는 안 바뀌었는데 재고만 3개 더 사라졌다. 한 번 더 누르면 3개 더 사라진다.

`orders/models.py`의 `Refund.auto_or_escalate()`를 열어 본다.
금액 한 줄만 있다. 7일도, 주문 상태도 검사하지 않는다.
`Order.mark_paid()`도 열어 본다. 재고는 `stock__gte` 조건부 UPDATE로 꼼꼼히 지키면서,
**주문이 어떤 상태였는지는 묻지 않는다**. 그냥 `status = PAID`로 덮어쓴다.

> 부탁은 있었다. **보장이 없었다.**
> 프롬프트에 세 문장을 쓴 사람은 규칙을 만들었다고 믿었지만,
> 세계는 그 문장을 한 번도 읽지 않았다.

이 간격에 이름이 있다 — **세계 부채**. 8단계에서 이 부채를 자동으로 세어 본다.

채점표도 같은 말을 한다.

```bash
just test 04     # 19개 중 1개만 통과한다 (6 failed, 12 errors)
```

통과하는 하나는 `test_정상_전이는_그대로_통과한다`다.
지금 세계도 **정상적인 결제는 잘 처리한다**. 문제는 정상이 아닌 요청이다.

통과하지 못한 18개는 성격이 둘로 갈린다. 섞어서 세면 안 된다.

- **행동 증거 3개** — 카드 ⑤⑥②의 HTTP 테스트. 세계에 실제로 요청을 넣었더니
  막지 못했다는 실측이다. 위에서 눈으로 본 것과 같은 사건이다.
- **제출 계약 검사 15개** — 12개는 `orders.rules`·`orders.verdict` 모듈이 아직
  없어서 나는 `ERROR`(수집 단계 실패), 3개는 `RULES.md` 대장 검사다.
  "아직 안 만들었다"는 뜻이지 "세계가 법을 어겼다"는 실측이 아니다.

그리고 하나 더 — 카드 ⑤⑥은 **고정 fixture** 다. 실제 LLM 이 프롬프트에
불복종하는 것을 관찰한 것이 아니라, 불복종하는 응답을 **가정하고** 서버에
넣어 본 것이다. 우리가 보는 것은 모델의 성향이 아니라 세계의 보장 부재다.

## 수정 — 세 문장을 코드로 이사시킨다

옮길 곳은 이미 다 있다. Django가 준 것은 **자리와 도구**다.

| 필요한 것 | Django가 준 자리 |
|---|---|
| 판정을 어디에 쓰나 | 모델 메서드(`Refund.decide`) |
| "지금 상태가 X일 때만" | 조건부 `UPDATE` + `rowcount` |
| 중간에 실패하면 되돌리기 | `transaction.atomic()` |
| 판정을 밖에 알리기 | HTTP 상태 코드 |

### 1. 판정 계약 타입 — `orders/verdict.py`

판정은 참/거짓이 아니다. 세 값이다.

| kind | 뜻 | HTTP |
|---|---|---|
| `ALLOW` | 규칙이 확정했다 | 200 (자원을 만들었으면 201도 쓴다) |
| `DENY` | 세계가 거부했다 | **409** |
| `ESCALATE` | 사람에게 올린다 | 202 |

그리고 **어떤 규칙이 그렇게 판정했는지(`rule_ids`)**와
**대신 갈 수 있는 길(`alternatives`)**을 함께 담는다.
거절만 하고 길을 안 알려주면 AI 직원은 우회를 시도한다 — 이건 사람도 같다.

```python
@dataclass(frozen=True)
class Verdict:
    kind: str
    rule_ids: list[str]
    reason: str
    alternatives: list[str]
```

403(권한 없음)과 409(상태가 안 맞음)는 다른 말이다.
1단계의 403은 "너는 그럴 자격이 없다"였고, 여기 409는
"자격은 있지만 **세계가 지금 그 상태가 아니다**"다.

### 2. 임계값과 규칙 ID — `orders/rules.py`

```python
REFUND_WINDOW_DAYS = 7
ESCALATE_OVER = 50_000

REFUND_001 = 'REFUND-001@v1'   # 결제 후 7일이 지난 주문은 환불하지 마라
REFUND_002 = 'REFUND-002@v1'   # 5만원 초과 환불은 점주 승인
ORDER_001 = 'ORDER-001@v1'     # pending 에서만 paid 로 간다
```

숫자를 상수로 빼는 이유는 예뻐서가 아니다. **버전을 붙이기 위해서**다.
7일이 10일로 바뀌면 `REFUND-001@v2`가 생기고 `@v1`은 `deprecated`가 된다.
그때 "언제부터 10일이었나"에 답할 수 있어야 한다.

### 3. `Refund.decide()` — 규칙을 코드로

`auto_or_escalate()`를 지우고 `decide()`로 바꾼다. 순서가 중요하다 —
**7일을 먼저 본다.** 기한이 지난 건은 금액이 얼마든 격상 대상이 아니라 거부 대상이다.

- 7일 초과 → `DENY`, `rule_ids=[REFUND_001]`
- 5만원 초과 → `ESCALATE`, `rule_ids=[REFUND_002]`
- 그 외 → `ALLOW` → 자동 승인. 단 `decided_by`는 비우고 `decided_via='rule'`로 남긴다.
  **사람이 확정한 것과 규칙이 확정한 것은 다른 사건이다**(7단계 장부의 소재).

기한 비교에서 `.days`로 자르지 마라. `(now - created_at).days > 7`은 7일 23시간을
"7일"로 만들어 통과시킨다. `timedelta(days=7)`과 통째로 비교해야
정확히 7일까지 허용하고 **초과분만** 거부한다.

기한을 **언제 기준으로** 재는지도 지금 정해 둔다. 이 세계의 약속은 둘이다.

- 판정 기준 시점은 **신청 시점**이다. 승인 큐에서 기다리다 기한을 넘긴 고액 건을
  승인 시점에 다시 검사하지는 않는다(그 재검사는 5단계 소재다).
- 결제 시각을 따로 안 들고 있어서 **결제일 = `created_at`(주문 생성 시각)** 으로 본다.
  교육상 가정이고, `paid_at`은 7단계 장부에서 생긴다.

**`alternatives`는 실제로 갈 수 있는 길만 적는다.** 없는 길을 적으면 그건
대안이 아니라 거짓말이고, AI 직원은 그 거짓말을 그대로 시도한다.
이 세계에는 예외 승인 큐도, 교환·재발송 경로도 아직 없다 — 그러니 기한 초과
`DENY`의 대안은 조회 경로 하나뿐이다. 고액 `ESCALATE`에 "5만원 이하로 쪼개서
다시 올려라"를 적어서도 안 된다. 그건 대안이 아니라 **승인 회피 안내**다.
줄 길이 없으면 **빈 목록**이 정직한 답이다.

### 4. `Order.mark_paid()` — 전이 계약

```python
moved = Order.objects.filter(pk=self.pk, status=Status.PENDING).update(status=Status.PAID)
if not moved:
    raise InvalidTransition(...)
```

3단계 `update()`와 같은 모양이다. 다른 점은 `WHERE`에 **현재 상태**가 들어간 것뿐이다.
UPDATE는 자기가 몇 행을 바꿨는지 돌려준다.

그 숫자가 0이면 무슨 뜻인가. 정확히 하나다 —
**대상 PK이면서 pending인 행이 없다.** 다른 요청이 먼저 지나갔을 수도 있고,
애초에 pending이 아니었을 수도 있다. rowcount 0 자체는 경합의 증거가 아니라
**조건 불일치**의 증거다. 거부 사유에도 그렇게 적는다. 이때 `self.status`를
꺼내 "현재 결제 완료입니다"라고 쓰면 안 된다 — 그건 재조회하지 않은 메모리 위의
값이고, DB의 현재 상태라고 말할 자격이 없다.

두 가지를 지킨다.

- 전부 `transaction.atomic()` 안에서 한다. 중간에 실패하면 상태 전이도, 이미 깎은
  앞 상품의 재고도 함께 되돌아간다.
- **재고 차감 전에** 상태 전이를 판정한다. 롤백 때문이 아니다(같은 트랜잭션이라
  어느 순서든 예외가 나면 함께 되돌아간다). 어차피 거부할 요청에 **불필요한 재고
  갱신을 하지 않기 위해서**다.

환불 쪽에도 같은 원자성이 필요하다. 제안 생성 → 승인 → 주문 취소가 따로 커밋되면,
마지막이 깨졌을 때 **승인된 환불과 취소되지 않은 주문**이 공존한다. 장부는
"환불했다"는데 주문은 살아 있는 상태다. `Refund.approve()` 자체를 트랜잭션으로
감싸 두면 admin이나 shell에서 직접 불러도 같은 보장을 받는다.

### 5. 뷰 — 판정을 밖으로

콘솔의 환불 제안이 `Verdict`를 그대로 응답한다.

- 브라우저(HTML): `ALLOW`·`ESCALATE`는 콘솔로 되돌아가고, `DENY`는 **409 화면**을 띄운다.
- API(`Accept: application/json`): `kind`·`rule_ids`·`reason`·`alternatives` JSON을
  200/201·202·409로 응답한다. 4단계 이후 실접속 트랙의 MCP 클라이언트가 읽을 형식이다.

여기서 한 가지를 더 갈라 둔다. **판정과 결과는 다른 값이다.**
`ALLOW`는 "허용된다"는 판정일 뿐이고, 세계가 실제로 움직였는지는 따로 말해야 한다
(`Outcome`: 아무것도 안 씀 / 큐에 올림 / 확정 커밋 / 이미 처리된 건).
둘을 섞으면 이런 거짓말이 나온다 — 점주가 이미 승인한 고액 환불에 대고
같은 요청을 또 넣었을 때, 다시 판정해서 "격상 대상입니다"라고 답하는 것.
그건 판정이 아니라 **현실을 안 본 것**이다. 이미 있는 건에는 **지금의 처리 상태**를 답한다.

### 6. 규칙 대장 — `RULES.md`

코드만 고치고 끝내면 반쪽이다. **이사한 규칙은 대장에 남긴다.**
행 하나에: ID · 원문(프롬프트 문장 그대로) · 출처 · 시행 형식 · 코드 위치 · 검증 테스트 · 상태.

그리고 `agent/prompts/ai_staff.md`의 세 문장은 **지우지 않는다.**
옆에 `→ 코드로 이사됨(REFUND-001@v1)` 주석만 단다.
프롬프트의 금지문과 시행 코드를 대조하는 것이 8단계 **세계 부채 리포트**의 입력이다.

## 검증

```bash
just test 04
uv run pytest            # 0~3단계도 그대로 통과해야 한다
```

콘솔에서 다시 누른다.

| 카드 | 이사 전 | 이사 후 |
|---|---|---|
| ② 5.4만원 환불 제안 | 점주 승인 대기 | 그대로 — 202 ESCALATE(`REFUND-002@v1`) |
| ⑤ 8일 지난 환불 | 자동 승인·주문 취소 | **409** `REFUND-001@v1: 결제 후 7일 초과` |
| ⑥ 재결제 | 재고 이중 차감 | **409** `ORDER-001@v1: 결제 대기 상태가 아니다(조건 불일치)` |

⑥ 이후 재고를 다시 세어 본다. **안 깎였다.**
같은 fixture, 같은 요청, 같은 악의. 달라진 것은 세계뿐이다.

## 이 단계의 한 문장

> **Django는 이 법을 써주지 않았다.**
> 하지만 **어디에 쓸지**(모델 메서드·조건부 UPDATE·rowcount)와
> **지켜줄 방법**(트랜잭션)은 이미 있었다.

3단계 질문의 답이기도 하다. 주문 상태에는 `CHECK`가 없다 —
재고는 "언제나 0 이상"이라는 **불변식**이라 한 줄로 새길 수 있었지만,
주문 상태는 "지금이 어디냐에 따라 갈 수 있는 곳이 다르다"는 **전이 계약**이라
한 줄로는 안 되고, 대신 **조건부 UPDATE + rowcount** 라는 자리가 있었다.

### 다만, 이 법이 지켜지는 범위

3단계의 `CHECK ("stock" >= 0)`와 오늘 심은 법은 **층이 다르다.**
재고 제약은 DB가 지킨다 — 어느 경로로 오든 뚫리지 않는다. 오늘의 세 법은
**애플리케이션 경로 계약**이다. `Refund.decide()`를 지나고 `mark_paid()`를 지날 때만
시행된다. shell에서 `Order.objects.filter(...).update(status='paid')`를 때리거나
admin에서 `Refund.approve()`를 직접 부르면 **판정을 지나지 않는다.**

그래서 `RULES.md`에 "적용 경로 / 우회 가능 경로" 열이 있다.
법을 심었다고 쓰는 것으로 끝이 아니라, **어디까지 지켜지는지**를 함께 적는 것이
정직한 대장이다. 무엇을 DB 제약으로 올릴지는 7단계에서 다시 만난다.

## 관통 문장을 다듬는다 — "확정은 사람"이 정확한가

이 과정의 관통 문장은 **제안은 AI, 판정은 세계, 확정은 사람**이었다.
그런데 오늘 만든 것은 3만원짜리를 사람 없이 자동 승인한다.
그럼 "확정은 사람"은 틀린 건가?

아니다. 한 겹을 더 봐야 한다.

> **사람이 승인한 정책 범위는 규칙이 자동 확정하고, 격상 건은 사람이 확정한다.**

"5만원 이하는 자동으로 처리해도 좋다"고 정한 것 자체가 **점주의 결정**이다.
그 결정의 물증이 `RULES.md`의 **출처** 열이다 — 누가·언제 이 규칙을 말했는가.
`decided_via='rule'`로 남기는 이유도 여기 있다. 규칙이 확정한 사건과 사람이
확정한 사건은 **다른 사건**이고, 규칙이 확정한 사건의 배후에는 그 규칙을 승인한
사람이 있다. 대장에 출처가 없으면 그 배후가 사라지고, 그때는 진짜로
"기계가 혼자 정했다"가 된다.

## 이 단계가 보장하지 않는 것

법을 심었다고 세계가 안전해진 것은 아니다. 지금 **막지 못하는 것**을 적어 둔다.
알면서 남겨 둔 것이고, 뒤 단계의 소재다.

| 못 막는 것 | 지금 일어나는 일 | 어디서 |
|---|---|---|
| 같은 주문에 환불 두 번 신청 | 승인된 환불이 두 개 생긴다(콘솔이 걸러 줄 뿐, 세계가 막는 게 아니다) | 5단계 — 멱등키·유일성 제약 |
| 동시에 들어온 두 제안 | 둘 다 승인될 수 있다. 잠그지 않는다 | 5단계 — 경합 직렬화 |
| 승인 시점의 기한 재검사 | 신청 때만 본다. 큐에서 기다리다 8일이 돼도 그대로 승인된다 | 5단계 |
| DB 잠금 실패 | `OperationalError`가 그대로 올라간다. 재시도도, 사용자용 응답도 없다 | 5단계 |
| 누가·무엇으로 확정했는가의 장부 | `decided_via` 한 칸뿐이다. 판정·규칙 버전·상관 ID는 안 남는다 | 7단계 |
| 결제 시각 | 없다. `created_at`을 결제일로 쓰는 가정 위에 서 있다 | 7단계 — `paid_at` |
| 경로 밖 호출(shell·admin 직접 조작) | 판정을 지나지 않는다 | 7·8단계 — DB 제약·부채 리포트 |

4단계 완료는 "실접속에 필요한 보장이 완성됐다"는 뜻이 **아니다.**
전이 계약 하나가 켜져서 이제 진짜 LLM을 붙여 **관찰**해도 되는 시점이라는 뜻이다.

### 2. 이사 비용 — 한 줄

```bash
git diff stage-04-start stage-04-done --stat
```

> 프롬프트 세 문장을 코드로 옮기는 데 **파일 N개 / M줄**이 들었다.

앱 코드만 따로 세는 명령과 단계별 누적표는 [단계 색인의 이사 비용표](README.md)에 있다.
이 숫자가 이 과정에서 계속 물을 질문의 답이다 —
"세계에 법 하나를 심는 원가는 얼마인가."
단, **LOC는 변경량이지 시간·유지비의 증명이 아니다.** 줄 수로 "그래서 싸다"까지
말하지 않는다.

### 3. 설명 — 왜 이 순서인가

> **왜 상태 UPDATE가 재고 차감보다 먼저인가? 그리고 두 상품짜리 주문에서
> 뒤 상품의 재고가 모자라면, 이미 깎은 앞 상품의 재고는 어떻게 되는가?**

"순서가 뒤집히면 재고가 이미 깎여 있다"는 답은 **틀렸다** — 둘 다 같은
트랜잭션 안이라 예외가 나면 어느 순서든 함께 되돌아간다. 그럼 순서의 진짜
이유는 무엇인지, 그리고 롤백이 무엇을 어디까지 되돌리는지를 자기 말로 쓴다.
`tests/stage_04_transition_contract.py::test_뒤_상품에서_재고가_모자라면_앞_상품_차감도_돌아온다`
를 읽고 답해도 좋다.
